Aula 13 — Propagação de erros, human review e proveniência

Domínio 5 · Context Management & Reliability (15%) ~60 min
🎯 Objetivo do dia. Dominar três Task Statements de confiabilidade: 5.3 (como erros devem viajar de subagents para o coordinator), 5.5 (revisão humana roteada por confiança calibrada) e 5.6 (preservar a proveniência — quem disse o quê — ao longo da síntese multi-fonte). É a aula que transforma "pipeline que funciona no happy path" em sistema que se comporta bem quando algo falha.

1. Propagação de erros estruturada (Task Statement 5.3)

Num sistema multi-agent, uma falha num subagent é informação, não um desastre. A pergunta da prova é sempre a mesma: o que o coordinator recebe quando algo quebra? A resposta correta é contexto de erro estruturado com quatro campos:

  • failure type — o tipo de falha (timeout, rate limit, permissão negada)
  • attempted query — o que foi tentado (a query, o documento, os parâmetros)
  • partial results — o que já foi obtido antes da falha
  • alternative approaches — alternativas possíveis (outra fonte, query mais estreita)
// O que o web search subagent devolve ao coordinator quando falha:
{
  "status": "partial_failure",
  "failure_type": "timeout",                 // tipo de falha
  "attempted_query": "site:gov.br PIB setores 2025",
  "partial_results": [ /* 3 fontes já coletadas */ ],
  "alternatives": ["retry com query mais curta",
                   "usar fonte secundária (IBGE press release)"]
}

Com esse payload, o coordinator consegue decidir de forma inteligente: retentar com outra query, tentar uma fonte alternativa, ou seguir com os resultados parciais e marcar a lacuna na síntese.

Access failure ≠ empty result válido

Uma falha de acesso (timeout, serviço fora) exige decisão de retry: a resposta existe, só não chegou. Um resultado vazio válido é uma query bem-sucedida que simplesmente não teve matches — é informação ("não há resultados para X"), não falha. Confundir os dois corrompe a decisão do coordinator: ele pode retentar uma query que já respondeu "não existe", ou aceitar como vazio um resultado que na verdade falhou.

Os três anti-padrões (decora isso)

  • ❌ Suprimir o erro: capturar a exceção e devolver um resultado vazio marcado como sucesso. O coordinator acha que "não há nada sobre o tema" e produz uma pesquisa silenciosamente incompleta.
  • ❌ Derrubar tudo: propagar a exceção até um handler de topo que termina o workflow inteiro por causa de UMA falha recuperável.
  • ❌ Status genérico: devolver só "search unavailable" — esconde do coordinator o contexto que permitiria uma recuperação informada. Retry interno com backoff é legítimo, mas o que sobe depois de esgotado precisa ser o contexto estruturado, não uma string vaga.

Recovery local primeiro; propaga só o irrecuperável

A regra de divisão de trabalho: o subagent resolve localmente falhas transitórias (retry com backoff, query reformulada). Só sobe para o coordinator o que ele não conseguiu resolver — e sempre acompanhado do que foi tentado e dos resultados parciais. O coordinator então decide o destino global (re-delegar, trocar de fonte, ou seguir com lacuna anotada).

Coverage annotations na síntese

Quando o coordinator decide seguir com parciais, a síntese precisa anotar a cobertura: quais findings estão bem suportados e quais áreas têm gaps por fontes indisponíveis. O relatório final deve dizer explicitamente "a seção sobre regulação europeia está incompleta porque a fonte primária falhou" — nunca deixar a lacuna invisível.

2. Human review e calibração de confiança (Task Statement 5.5)

Contexto típico da prova (cenário 6): um pipeline de extração que afirma 97% de acurácia agregada. O número é real — e mesmo assim enganoso. Acurácia agregada mascara segmentos ruins: pode ser 99,5% em notas fiscais padrão e 71% em contratos manuscritos. Antes de automatizar (reduzir revisão humana), meça a acurácia por tipo de documento e por campo.

O fluxo correto de revisão humana

  1. Confidence por campo: o modelo emite um score de confiança por campo extraído, não um número global por documento.
  2. Calibração com validation set rotulado: os scores brutos do modelo não são probabilidades reais. Use um conjunto de validação rotulado para calibrar os thresholds de roteamento (ex.: "abaixo de 0,82 no campo valor_total → fila humana").
  3. Roteamento: extrações low-confidence e documentos ambíguos ou contraditórios vão para revisão humana — priorizando a capacidade limitada dos revisores onde o modelo é fraco.
  4. Stratified random sampling: mesmo as extrações high-confidence (que vão direto, sem revisão) precisam de amostragem aleatória estratificada contínua — por tipo de documento e campo — para medir a taxa de erro real e detectar padrões de erro novos que o threshold não captura.
{
  "document_type": "contrato_manuscrito",
  "fields": {
    "partes":       { "value": ["...", "..."], "confidence": 0.94 },
    "valor_total":  { "value": 185000,          "confidence": 0.61 },  // → fila humana
    "data_vigencia":{ "value": null,            "confidence": 0.30 }   // → fila humana
  }
}

Ponto sutil que a prova cobra: confidence autorreportada sem calibração é mal calibrada (o modelo costuma estar confiante justamente nos casos difíceis). Por isso o threshold nasce do validation set rotulado, não da intuição. E o sampling dos high-confidence não é redundância — é o mecanismo que revela erros que a própria confiança não percebe.

Calibração é por campo

Um threshold único para todos os campos é intuição disfarçada de regra: cada campo erra num nível de confiança diferente (o cnpj a 0,80 quase sempre certo; o valor_total a 0,92 ainda errando). Calibre o threshold de cada campo com o validation set rotulado e, como a capacidade dos revisores é limitada, priorize a fila: primeiro as extrações de baixa confiança e os documentos ambíguos ou contraditórios.

Regra de bolso: o threshold vem dos dados rotulados, campo a campo — nunca do chute nem de uma instrução pedindo ao modelo para "ser mais humilde".

3. Proveniência e incerteza na síntese multi-fonte (Task Statement 5.6)

Quando findings passam por etapas de sumarização, a atribuição de fonte se perde: três fontes viram "estudos indicam que...". A defesa arquitetural é exigir dos subagents claim-source mappings estruturados — cada claim com URL/nome do documento, trecho relevante e data — e exigir que a síntese preserve e mescle esses mappings ao combinar findings.

{
  "claim": "Adoção de IA generativa em agências de publicidade chega a 62%",
  "evidence_excerpt": "62% das agências entrevistadas relatam uso regular...",
  "source_url": "https://exemplo.com/pesquisa-2026",
  "publication_date": "2026-03-14"
}

Estatísticas conflitantes de fontes críveis

Duas fontes respeitáveis dizem "62%" e "41%"? A tentação (e o distrator clássico) é escolher um valor — o mais recente, o mais conservador, a média. Errado. A resposta certa: anotar os dois valores, cada um com sua fonte e seu contexto metodológico, e deixar a divergência visível. O document analysis agent completa a análise com os valores conflitantes incluídos e anotados; quem decide como reconciliar é o coordinator, antes da síntese. Abortar a análise com "dados inconsistentes" é o anti-padrão simétrico: joga fora evidência legítima e o tema some do relatório.

Regra de bolso: conflito se anota e sobe; quem reconcilia é o coordinator, nunca uma heurística do subagent.

Datas de publicação: diferença temporal não é contradição

"41%" de 2023 e "62%" de 2026 podem não ser conflito nenhum — pode ser crescimento real. Sem a data de publicação/coleta no output estruturado, a síntese interpreta diferença temporal como contradição. Por isso publication_date entra em todo mapping: o subagent é obrigado a reportá-la. Se a fonte não traz data, o valor é null (de preferência com o motivo), nunca uma data inventada — campo required sem null induz fabricação (aula 10, TS 4.3).

Estrutura do relatório final

A síntese deve separar explicitamente findings estabelecidos (múltiplas fontes convergem) de findings contestados (fontes divergem — com as caracterizações originais preservadas). Um aviso genérico no topo ou um "pode ser" aplicado a tudo não resolve: o leitor continua sem saber qual achado é sólido e qual é disputado.

E cada tipo de conteúdo vai no formato que lhe serve — não achatar tudo num formato uniforme:

  • dados financeiros → tabela (comparação lado a lado)
  • notícias e sequência de eventos → prosa (contexto e encadeamento)
  • achados técnicos → lista estruturada (itens verificáveis um a um)

Regra de bolso: o leitor precisa ver o grau de certeza de cada achado e ler cada tipo de conteúdo no formato natural dele — uniformidade de formato não é virtude.

⚠️ Pegadinha do dia

Questões de erro em multi-agent vêm com dois distratores simétricos e sedutores: "catch e retornar vazio como sucesso" (parece robusto, mas suprime informação e gera pesquisa silenciosamente incompleta) e "propagar a exceção e encerrar o workflow" (parece seguro, mas mata o trabalho todo por uma falha recuperável). O terceiro distrator é o status genérico tipo "search unavailable", que esconde o contexto do coordinator. Regra de bolso: erro sobe como dado estruturado (tipo + tentativa + parciais + alternativas), nunca como silêncio, nunca como exceção fatal, nunca como string vaga. E em questões de acurácia: número agregado bonito (97%) nunca é prova suficiente — segmente por tipo de documento e campo antes de tirar o humano do loop.

Your web search subagent queries a source and receives zero matching documents. A teammate wants to treat this the same way as a timeout: retry three times, then escalate to the coordinator as a failure. What is wrong with this design?
