Aula 07 — Slash commands, skills e plan mode

Domínio 3 · Claude Code Configuration & Workflows (20%) Task Statements 3.2 e 3.4 ~60 min
🎯 Objetivo do dia. Saber onde criar comandos e skills (projeto vs pessoal) e quando usar cada mecanismo: slash command versionado, skill com frontmatter (context: fork, allowed-tools, argument-hint), CLAUDE.md, hook ou regra de permissão em settings.json. E dominar a decisão plan mode vs execução direta por escopo, risco e exigência de aprovação humana — incluindo o papel do Explore subagent para proteger o contexto da conversa principal.

1. Slash commands: escopo de projeto vs escopo de usuário (TS 3.2)

Um custom slash command é um arquivo Markdown cujo conteúdo vira o prompt quando você digita /nome-do-comando. A única decisão arquitetural que a prova cobra aqui é onde o arquivo mora — e a resposta depende de quem deve recebê-lo:

  • .claude/commands/ dentro do repositório → escopo de projeto. Vai pro version control (git), então todo dev que clona ou dá pull recebe o comando automaticamente. É o lugar de qualquer workflow padronizado do time: /review, /deploy-check, /novo-endpoint.
  • ~/.claude/commands/ no home do usuário → escopo pessoal. Não entra no repo, não é compartilhado. É o lugar dos seus atalhos individuais.
meu-repo/
└── .claude/
    └── commands/
        └── review.md        ← /review disponível pra todo mundo que clonar

~/                      (fora do repo)
└── .claude/
    └── commands/
        └── meu-resumo.md    ← comando pessoal, só existe na sua máquina

Regra de bolso da prova: o stem disser "available to every developer when they clone" ou "shared with the team" → a resposta é .claude/commands/ no repositório. Qualquer opção com ~/ está errada nesse cenário porque não passa pelo version control.

2. Skills: SKILL.md com frontmatter (TS 3.2)

Uma skill é um pacote de instruções especializadas que o Claude carrega sob demanda (quando a tarefa pede), em vez de ocupar contexto o tempo todo. Vive em .claude/skills/<nome>/SKILL.md (projeto) ou ~/.claude/skills/<nome>/SKILL.md (pessoal). O SKILL.md tem frontmatter YAML com três campos que a prova cobra nominalmente:

---
name: analise-codebase
description: Analisa a estrutura do repositório e gera relatório de dependências
context: fork
allowed-tools: Read, Grep, Glob, Write
argument-hint: "caminho-do-diretorio (ex.: src/api)"
---

# Instruções da skill em Markdown...
  • context: fork → a skill roda num sub-agent isolado. O output verboso (ex.: análise de codebase inteira, brainstorming de alternativas) não polui a conversa principal — só o resultado/resumo volta. É o equivalente em skill do Explore subagent.
  • allowed-tools → restringe quais tools a skill pode usar durante a execução. Caso clássico da prova: limitar a operações de escrita/leitura para impedir ações destrutivas (uma skill de refatoração sem acesso a Bash não roda rm -rf).
  • argument-hint → texto exibido quando o dev invoca a skill sem os parâmetros obrigatórios, lembrando o que passar (ex.: qual diretório analisar).
🧭 Prova × produto atual (documentação do Claude Code conferida em 22/10/2026)
  • Comandos e skills: no produto atual, os custom commands foram unificados com as skills; os arquivos em .claude/commands/ continuam funcionando. A prova trata os dois como mecanismos distintos (seção 1 e seção 2).
  • allowed-tools: o guia (TS 3.2) diz que o campo restringe as tools durante a skill — e é assim que a prova cobra. No produto atual ele faz outra coisa: só pré-aprova as tools listadas, que rodam sem pedir permissão no turno que invoca a skill, e não tira nenhuma tool do alcance. Para remover tools enquanto a skill está ativa existe outro campo, disallowed-tools.
  • context: fork: a skill roda num subagent que não vê o histórico da sua conversa e devolve um resumo ao terminar — o isolamento que o guia descreve.
Na prova, responda como o guia: allowed-tools restringe as tools da skill.

Variante pessoal sem afetar o time

Quer customizar uma skill do projeto só pra você? Crie uma variante em ~/.claude/skills/ com um nome diferente (ex.: analise-codebase-luo). Nome diferente = não colide com a do time e não altera o comportamento dos colegas. Editar a skill do repo mudaria o workflow de todo mundo — e commitar sua preferência pessoal é exatamente o anti-padrão que a prova testa.

Skill vs CLAUDE.md: a decisão que cai na prova

Skill (.claude/skills/)CLAUDE.md
CarregamentoOn-demand: invocada quando a tarefa pedeSempre carregado em toda sessão
Uso idealWorkflows específicos de uma tarefa (análise, migração, release)Padrões universais do projeto (estilo, convenções, "nunca faça X")
Custo de contextoSó quando usadaPermanente — crescer demais polui tudo

Se o stem diz "padrão que vale pra todo código do projeto" → CLAUDE.md. Se diz "workflow que roda às vezes, com parâmetros e output grande" → skill (provavelmente com context: fork).

Mapa rápido: qual mecanismo para cada necessidade

A prova gosta de listar várias necessidades e pedir o mecanismo de cada uma. O critério é sempre quando a orientação se aplica e quem deve recebê-la:

NecessidadeMecanismo
Padrão que vale para todo dev, em toda sessãoCLAUDE.md do projeto (sempre carregado, versionado)
Convenção de um tipo de arquivo espalhado pelo repo.claude/rules/ com paths glob (aula 06)
Workflow que roda às vezes, com parâmetros ou saída grandeSkill em .claude/skills/ (com context: fork se for verboso)
Prompt padronizado que o time dispara pelo nomeSlash command em .claude/commands/
Atalho só seu~/.claude/commands/ ou ~/.claude/skills/ (com nome próprio)
Algo que precisa acontecer sempre, sem exceção (ex.: rodar o linter depois de toda edição)Hook, configurado em settings.json — enforcement programático, não instrução; a lógica do TS 1.5 (aula 03)
Bloquear sempre um comando ou um arquivo (ex.: o .env, a pasta secrets/)Regra deny em permissions no .claude/settings.json do projeto (versionado)

As regras de permissão ficam em permissions (allow, ask, deny) nos arquivos de settings e são aplicadas pelo próprio Claude Code, antes de a tool rodar — não dependem do modelo seguir instrução:

// .claude/settings.json (no repo, vale para o time)
{
  "permissions": {
    "deny": ["Read(**/.env)", "Read(./secrets/**)"]
  }
}
  • Ordem de avaliação: deny → ask → allow. Entre regras, o deny sempre ganha. (Read(./.env) casa só com o do diretório atual; Read(**/.env), com todos.)
  • Precedência dos arquivos (do mais forte ao mais fraco): managed (política da organização) → argumentos de linha de comando → .claude/settings.local.json (pessoal, fora do git) → .claude/settings.json (projeto, versionado) → ~/.claude/settings.json (usuário). Listas como permissions.allow se combinam entre os arquivos em vez de se sobrescreverem — por isso um allow pessoal não reabre o que um deny do projeto fechou.
  • Hooks também se configuram nos arquivos de settings (e ainda em plugins e no frontmatter de skills e subagents). Hook é para executar algo num evento; regra deny é para impedir uma tool call.

Regra de bolso: sempre carregado → CLAUDE.md; depende do arquivo → rule com glob; sob demanda → skill ou comando; garantia → código, nunca texto: algo que tem de acontecer → hook; algo que nunca pode acontecer → regra deny. O caso oposto: a regra deny bloqueia sem olhar contexto — se a proibição depende de uma condição (só em produção, só acima de um valor), ela vira hook com lógica. E o deny cobre as tools nativas e os comandos que o Claude Code reconhece (cat, head), não um script que abre o arquivo por conta própria: para isso, sandbox.

3. Plan mode vs execução direta (TS 3.4)

Plan mode é o modo em que o Claude explora e planeja sem modificar nada: lê o código, mapeia dependências, propõe uma abordagem — e só executa depois da sua aprovação. A prova cobra a fronteira da decisão:

  • ✅ Plan mode quando a tarefa tem: mudanças em larga escala, múltiplas abordagens válidas, decisões arquiteturais (fronteiras de serviço, dependências entre módulos), modificação de muitos arquivos (ex.: migração de biblioteca em 45+ arquivos, monólito → microservices, escolha entre abordagens de integração com requisitos de infra diferentes).
  • ✅ Execução direta quando a mudança é simples e bem-escopada: um bug de um arquivo com stack trace claro, adicionar uma validação de data numa função, renomear uma variável.

O raciocínio econômico: plan mode previne retrabalho caro. Descobrir tarde demais que dois módulos são acoplados custa muito mais do que os minutos gastos explorando antes. Mas planejar uma mudança de 3 linhas é over-engineering de processo — o exame penaliza os dois extremos.

Além do escopo: risco e aprovação humana

Os objetivos oficiais da prova pedem para escolher entre plan mode, execução direta ou workflow multifase com base em "task scope, risk level, and human approval requirements". Escopo é o que a seção acima cobre; os outros dois critérios mudam a resposta mesmo quando a mudança é pequena:

CritérioAponta para plan mode quando…Aponta para execução direta quando…
Escopomuitos arquivos, várias abordagens válidas, decisão arquiteturalmudança pequena, bem entendida, um arquivo
Riscotoca produção, dados de cliente ou algo irreversível (migração que apaga coluna, script que remove registros)a mudança é reversível e os testes pegam o erro
Aprovação humanaalguém precisa aprovar antes do efeito (política, dono do dado, change advisory)ninguém precisa aprovar antes; review do PR basta

No plan mode, o plano é o ponto de aprovação: o humano lê o que vai acontecer antes de qualquer arquivo mudar. Sem humano no terminal, o mesmo vale no modo não interativo: claude -p --permission-mode plan "…" produz o plano sem editar nada; depois da aprovação, uma segunda execução aplica o plano aprovado. Quando a tarefa tem fases distintas (discovery → plano → implementação → verificação), a resposta é o workflow multifase da seção seguinte.

Regra de bolso: plan mode se qualquer critério pesa — escopo grande, risco alto ou aprovação exigida antes do efeito; execução direta só quando os três estão baixos. O caso oposto: mudança pequena e reversível, sem aprovação prévia exigida, vai direto mesmo em código importante — planejar 3 linhas continua sendo over-engineering de processo.

Explore subagent: protegendo o contexto

Fases de discovery ("onde essa função é usada?", "mapeie todos os callers") geram output enorme: dezenas de arquivos lidos, greps, listagens. Se isso entra na conversa principal, a janela de contexto acaba antes da fase de implementação. O Explore subagent resolve: faz a busca verbosa num contexto isolado e devolve só o resumo. Mesma lógica do context: fork das skills.

Onde isso cai na prova: tarefas multifase. Para uma mudança grande num código que você não conhece, o fluxo proporcional é: discovery no Explore subagent (buscas e leituras ficam isoladas; volta um resumo) → plan mode para escolher a abordagem a partir desse resumo → execução direta do plano aprovado. Sem o Explore, a saída do discovery enche a janela e a implementação começa com o contexto esgotado: decisões tomadas no meio do caminho se perdem.

Regra de bolso: discovery verboso não mora na conversa principal — roda isolado e entrega só o resumo.

Combinando os dois (o padrão "certo" da prova)

Para tarefas grandes, o fluxo proporcional é: plan mode para investigação e desenho → execução direta para implementar o plano aprovado. Não é "plan mode pra sempre" nem "execução direta desde o início" — é cada modo na fase em que ele é forte. Distrator clássico: "começar em execução direta e trocar pra plan mode se aparecer complexidade" — errado quando a complexidade já está declarada no requisito.

⚠️ Pegadinha do dia

Dois padrões de distrator dominam este tema. (1) Escopo errado: a questão pede algo "disponível pra todo o time" e oferece ~/.claude/... como opção — pessoal nunca é compartilhado, e "mandar cada dev copiar o arquivo" ignora o version control. (2) Plan mode como reflexo ou como fallback: "usar plan mode para toda tarefa" (over-engineering de processo) e "começar direto e trocar se complicar" (a complexidade já está no enunciado) são os dois errados simétricos. (3) Proibição como texto: "never read .env" no CLAUDE.md ou numa rule — instrução é probabilística; bloqueio garantido é regra deny no settings.json versionado. Regra de bolso: compartilhado = dentro do repo e versionado; planeje quando há mudança em larga escala, várias abordagens válidas, decisão arquitetural ou muitos arquivos (ex.: migração em 45+ arquivos, monólito → serviços), e também quando a mudança é pequena mas arriscada ou exige aprovação antes do efeito (ex.: script que apaga dados em produção); execute direto quando a mudança é simples, reversível, de escopo claro e sem aprovação prévia exigida (ex.: bug de um arquivo com stack trace claro).

Questão 9 · múltipla escolha Code Generation with Claude Code
To meet a retention policy, a nightly script must start deleting customer records older than seven years. The edit is one line in one file, but the script runs against the production database, deletions cannot be undone, and the policy requires the data owner to approve any deletion logic before it runs. How should you use Claude Code for this change?
Para cumprir uma política de retenção, um script noturno precisa passar a apagar registros de clientes com mais de sete anos. A edição é uma linha num arquivo, mas o script roda contra o banco de produção, as exclusões não podem ser desfeitas e a política exige que o dono do dado aprove qualquer lógica de exclusão antes de ela rodar. Como você deve usar o Claude Code nessa mudança?
Gabarito: B. Escopo não é o único critério: o risco (produção, exclusão irreversível) e a exigência de aprovação antes do efeito apontam para plan mode, mesmo numa mudança de uma linha. O plano é o ponto em que o dono do dado aprova o que vai acontecer; só depois a mudança é aplicada (sem humano no terminal, claude -p --permission-mode plan faz a mesma etapa). A decide só pelo escopo e ignora os outros dois critérios. C coloca a aprovação depois do merge — e a política pede aprovação antes de rodar, quando ainda dá para impedir a exclusão.
