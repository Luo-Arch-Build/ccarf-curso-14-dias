Aula 07 — Slash commands, skills e plan mode

Domínio 3 · Claude Code Configuration & Workflows (20%) Task Statements 3.2 e 3.4 ~60 min
🎯 Objetivo do dia. Saber onde criar comandos e skills (projeto vs pessoal) e quando usar cada mecanismo: slash command versionado, skill com frontmatter (context: fork, allowed-tools, argument-hint), CLAUDE.md, hook ou regra de permissão em settings.json. E dominar a escolha entre execução direta, plan mode e workflow multifásico, distinguindo supervisão, aprovação do plano e gates de produção/deploy — incluindo o papel do Explore subagent para proteger o contexto da conversa principal.

1. Slash commands: escopo de projeto vs escopo de usuário (TS 3.2)

Um custom slash command é um arquivo Markdown cujo conteúdo vira o prompt quando você digita /nome-do-comando. A única decisão arquitetural que a prova cobra aqui é onde o arquivo mora — e a resposta depende de quem deve recebê-lo:

  • .claude/commands/ dentro do repositório → escopo de projeto. Vai pro version control (git), então todo dev que clona ou dá pull recebe o comando automaticamente. É o lugar de qualquer workflow padronizado do time: /review, /deploy-check, /novo-endpoint.
  • ~/.claude/commands/ no home do usuário → escopo pessoal. Não entra no repo, não é compartilhado. É o lugar dos seus atalhos individuais.
meu-repo/
└── .claude/
    └── commands/
        └── review.md        ← /review disponível pra todo mundo que clonar

~/                      (fora do repo)
└── .claude/
    └── commands/
        └── meu-resumo.md    ← comando pessoal, só existe na sua máquina

Regra de bolso da prova: o stem disser "available to every developer when they clone" ou "shared with the team" → a resposta é .claude/commands/ no repositório. Qualquer opção com ~/ está errada nesse cenário porque não passa pelo version control.

2. Skills: SKILL.md com frontmatter (TS 3.2)

Uma skill é um pacote de instruções especializadas que o Claude carrega sob demanda (quando a tarefa pede), em vez de ocupar contexto o tempo todo. Vive em .claude/skills/<nome>/SKILL.md (projeto) ou ~/.claude/skills/<nome>/SKILL.md (pessoal). O SKILL.md tem frontmatter YAML com três campos que a prova cobra nominalmente:

---
name: analise-codebase
description: Analisa a estrutura do repositório e gera relatório de dependências
context: fork
allowed-tools: Read, Grep, Glob, Write
argument-hint: "caminho-do-diretorio (ex.: src/api)"
---

# Instruções da skill em Markdown...
  • context: fork → a skill roda num sub-agent isolado. O output verboso (ex.: análise de codebase inteira, brainstorming de alternativas) não polui a conversa principal — só o resultado/resumo volta. É o equivalente em skill do Explore subagent.
  • allowed-tools → restringe quais tools a skill pode usar durante a execução. Caso clássico da prova: limitar a operações de escrita/leitura para impedir ações destrutivas (uma skill de refatoração sem acesso a Bash não roda rm -rf).
  • argument-hint → texto exibido quando o dev invoca a skill sem os parâmetros obrigatórios, lembrando o que passar (ex.: qual diretório analisar).
🧭 Prova × produto atual (documentação do Claude Code conferida em 22/10/2026)
  • Comandos e skills: no produto atual, os custom commands foram unificados com as skills; os arquivos em .claude/commands/ continuam funcionando. A prova trata os dois como mecanismos distintos (seção 1 e seção 2).
  • allowed-tools: o guia (TS 3.2) diz que o campo restringe as tools durante a skill — e é assim que a prova cobra. No produto atual ele faz outra coisa: só pré-aprova as tools listadas, que rodam sem pedir permissão no turno que invoca a skill, e não tira nenhuma tool do alcance. Para remover tools enquanto a skill está ativa existe outro campo, disallowed-tools.
  • context: fork: a skill roda num subagent que não vê o histórico da sua conversa e devolve um resumo ao terminar — o isolamento que o guia descreve.
Na prova, responda como o guia: allowed-tools restringe as tools da skill.

Variante pessoal sem afetar o time

Quer customizar uma skill do projeto só pra você? Crie uma variante em ~/.claude/skills/ com um nome diferente (ex.: analise-codebase-luo). Nome diferente = não colide com a do time e não altera o comportamento dos colegas. Editar a skill do repo mudaria o workflow de todo mundo — e commitar sua preferência pessoal é exatamente o anti-padrão que a prova testa.

Skill vs CLAUDE.md: a decisão que cai na prova

Skill (.claude/skills/)CLAUDE.md
CarregamentoOn-demand: invocada quando a tarefa pedeSempre carregado em toda sessão
Uso idealWorkflows específicos de uma tarefa (análise, migração, release)Padrões universais do projeto (estilo, convenções, "nunca faça X")

Se o stem diz "padrão que vale pra todo código do projeto" → CLAUDE.md. Se diz "workflow que roda às vezes, com parâmetros e output grande" → skill (provavelmente com context: fork).

Mapa rápido: qual mecanismo para cada necessidade

A prova gosta de listar várias necessidades e pedir o mecanismo de cada uma. O critério é sempre quando a orientação se aplica e quem deve recebê-la:

NecessidadeMecanismo
Padrão que vale para todo dev, em toda sessãoCLAUDE.md do projeto (sempre carregado, versionado)
Convenção de um tipo de arquivo espalhado pelo repo.claude/rules/ com paths glob (aula 06)
Workflow que roda às vezes, com parâmetros ou saída grandeSkill em .claude/skills/ (com context: fork se for verboso)

Bloquear sempre um comando ou um arquivo (ex.: o .env, a pasta secrets/)Regra deny em permissions no .claude/settings.json do projeto (versionado)

As regras de permissão ficam em permissions (allow, ask, deny) nos arquivos de settings e são aplicadas pelo próprio Claude Code, antes de a tool rodar — não dependem do modelo seguir instrução:

// .claude/settings.json (no repo, vale para o time)
{
  "permissions": {
    "deny": ["Read(**/.env)", "Read(./secrets/**)"]
  }
}
  • Ordem de avaliação: deny → ask → allow. Entre regras, o deny sempre ganha. (Read(./.env) casa só com o do diretório atual; Read(**/.env), com todos.)
  • Precedência dos arquivos (do mais forte ao mais fraco): managed (política da organização) → argumentos de linha de comando → .claude/settings.local.json (pessoal, fora do git) → .claude/settings.json (projeto, versionado) → ~/.claude/settings.json (usuário). Listas como permissions.allow se combinam entre os arquivos em vez de se sobrescreverem — por isso um allow pessoal não reabre o que um deny do projeto fechou.
  • Hooks também se configuram nos arquivos de settings (e ainda em plugins e no frontmatter de skills e subagents). Hook é para executar algo num evento; regra deny é para impedir uma tool call.

Regra de bolso: sempre carregado → CLAUDE.md; depende do arquivo → rule com glob; sob demanda → skill ou comando; garantia → código, nunca texto: algo que tem de acontecer → hook; algo que nunca pode acontecer → regra deny. O caso oposto: a regra deny bloqueia sem olhar contexto — se a proibição depende de uma condição (só em produção, só acima de um valor), ela vira hook com lógica. E o deny cobre as tools nativas e os comandos que o Claude Code reconhece (cat, head), não um script que abre o arquivo por conta própria: para isso, sandbox.

3. Execução direta, plan mode e workflow multifásico (TS 3.4)

São três escolhas diferentes, não três nomes para o mesmo ciclo. Execução direta deixa o Claude agir nas tools permitidas; plan mode restringe a atuação do Claude a exploração e planejamento antes da implementação; workflow multifásico organiza fases explícitas com artefatos, handoffs e gates.

ArquiteturaEscolha quando…Controle e saída
Direct executionA mudança é simples, bem compreendida e bem delimitada: bug com stack trace claro, validação em uma função, renomear uma variável.O Claude edita/executa dentro das permissions. A revisão pode ser manual, edição por edição ou comando por comando; supervisão não transforma a tarefa em plan mode.
Plan modeO desenho ainda é incerto: múltiplas abordagens válidas, dependências desconhecidas, decisão arquitetural ou mudança em muitos arquivos.O Claude lê e explora sem modificar arquivos, produz um plano e só implementa depois da aprovação desse plano. A aprovação controla a transição do Claude, não autoriza produção ou deploy.
Multi-phase workflowO processo exige fases separadas, com responsáveis ou verificações independentes: discovery → aprovação → implementação → verificação → release.Cada fase entrega um artefato (relatório, plano, diff, evidência de testes) que é passado adiante por um handoff; gates humanos ou programáticos decidem se a fase seguinte pode começar.

Um único ciclo plano → execução é uma combinação útil de modos, mas não basta para definir um workflow multifásico. Esse workflow pode conter plan mode na fase de desenho, desde que existam outras fases explícitas, artefatos/handoffs e gates. A distinção segue a ideia de workflow como uma sequência predefinida de etapas especializadas na referência conceitual Workflows vs agents.

O raciocínio econômico continua valendo: planejar antes de uma mudança incerta previne retrabalho caro, mas planejar uma correção de três linhas já compreendida é over-engineering de processo. O exame penaliza tanto planejar tudo quanto começar direto uma tarefa cuja complexidade já está declarada.

Aprovação do plano ≠ gate de produção ou deploy

A aprovação do plano responde: "o Claude pode sair do planejamento e implementar esta proposta?". Uma exigência do dono do dado, do change advisory board ou de uma política de release responde outra pergunta: "esta mudança pode chegar ao ambiente ou produzir efeito externo?". Essa autorização precisa do processo externo correspondente — por exemplo, aprovação registrada no sistema de mudanças, proteção de ambiente, gate de CI/CD ou validação programática. Plan mode, sozinho, não fornece essa garantia.

Risco e revisão humana influenciam o desenho dos controles, mas não criam uma regra automática de modo. Uma edição simples pode usar execução direta supervisionada por permissions ask e revisão manual; uma mudança de alto risco pode exigir plan mode e gates externos; e um processo com aprovação, implementação e verificação independentes pede um workflow multifásico. Risco ou aprovação humana, isoladamente, não tornam plan mode suficiente.

Headless: o plano precisa ser retomado ou entregue

claude -p --permission-mode plan "…" pode produzir um plano sem editar arquivos, mas uma segunda execução headless não herda automaticamente a sessão nem o plano aprovado. Para implementar a mesma proposta, retome explicitamente a sessão correspondente ou forneça à nova execução o artefato/plano aprovado e o contexto necessário. Mesmo com esse handoff, aprovações de produção/deploy continuam sendo gates separados.

Regra de bolso: simples e compreendida → execução direta, ainda que supervisionada; desenho incerto → plan mode; fases predefinidas com artefatos, handoffs e gates → workflow multifásico. Um plano seguido de execução, sozinho, não é multifásico; aprovar o plano do Claude, sozinho, não aprova produção.

Explore subagent: protegendo o contexto

Fases de discovery ("onde essa função é usada?", "mapeie todos os callers") geram output enorme: dezenas de arquivos lidos, greps, listagens. Se isso entra na conversa principal, a janela de contexto acaba antes da fase de implementação. O Explore subagent resolve: faz a busca verbosa num contexto isolado e devolve só o resumo. Mesma lógica do context: fork das skills.

Num workflow multifásico, esse resumo pode ser o artefato de discovery entregue à fase de desenho. O plano aprovado vira outro artefato, recebido pela implementação; uma verificação independente produz evidências próprias antes do gate de release. O Explore protege o contexto, mas não substitui esses handoffs e gates.

Regra de bolso: discovery verboso não precisa morar na conversa principal — rode isolado e entregue um resumo útil à fase seguinte.

Compondo modos sem confundir as arquiteturas

Para uma tarefa grande de desenho incerto, plan mode → execução direta pode ser suficiente. Se o requisito também determinar discovery com relatório, aprovação formal, implementação e verificação independente, a resposta passa a ser workflow multifásico, possivelmente usando plan mode numa das fases. Não é o tamanho do prompt nem a quantidade de etapas mencionadas que decide: procure artefatos, handoffs e gates explícitos.

⚠️ Pegadinha do dia

Cinco padrões de distrator dominam este tema. (1) Escopo errado: algo disponível para todo o time vai no repo versionado, não em ~/.claude/.... (2) Modo como reflexo: plan mode para toda tarefa é over-engineering; começar direto uma complexidade já declarada também é erro. (3) Falso multifásico: um plano seguido de execução não basta; procure fases com artefatos, handoffs e gates. (4) Aprovação ou memória invisível: aprovar o plano do Claude não autoriza produção/deploy, e uma nova execução headless não herda o plano sem retomar a sessão ou receber o artefato. (5) Texto ou bloqueio errado: instrução não garante enforcement; use deny para proibição incondicional e hook com lógica quando a decisão depender do contexto.

Regra de bolso: compartilhado = repo versionado; mudança simples = execução direta, mesmo com revisão por edição; desenho incerto = plan mode; processo com handoffs e gates independentes = workflow multifásico.
