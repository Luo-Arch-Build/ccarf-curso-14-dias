Aula 02 — Orquestração multi-agent: coordinator e subagents

Domínio 1 · Agentic Architecture & Orchestration (27%) Task Statements 1.2 e 1.3 ~60 min
🎯 Objetivo do dia. Dominar o padrão hub-and-spoke: um coordinator que decompõe, delega e agrega, e subagents com contexto isolado que recebem tudo explicitamente no prompt. Você vai saber configurar allowedTools com "Task", definir AgentDefinitions, disparar subagents em paralelo e — o favorito da prova — diagnosticar quando o problema está na decomposição do coordinator, não nos subagents.

1. Hub-and-spoke: toda comunicação passa pelo coordinator (TS 1.2)

Num sistema multi-agent bem arquitetado, os subagents não conversam entre si. O coordinator é o hub: ele gerencia toda a comunicação inter-subagent, o tratamento de erros e o roteamento de informação. As pontas (spokes) são subagents especializados — um busca na web, um analisa documentos, um sintetiza, um gera o relatório.

Por que centralizar? Três motivos que a prova cobra:

  • Observabilidade — um único ponto onde você vê o que foi delegado, o que voltou e o que falhou
  • Tratamento de erro consistente — falhas de subagents sobem para um lugar que decide: retry, alternativa ou seguir com resultado parcial
  • Fluxo de informação controlado — o coordinator decide o que cada subagent precisa saber, em vez de todo mundo ver tudo

O atalho tentador é deixar um subagent chamar outro direto ("economiza um turno do coordinator"). O preço aparece na primeira falha: o erro morre na ponta, o coordinator nunca fica sabendo e ninguém consegue reconstruir o que foi feito. Logs, filas compartilhadas ou retries locais não devolvem ao coordinator o papel de decidir. Regra de bolso: subagent fala com o coordinator, nunca com outro subagent.

Os 4 papéis do coordinator

  1. Decomposição — quebrar a query do usuário em subtarefas que cubram o tópico inteiro
  2. Delegação — atribuir cada subtarefa ao subagent certo, particionando o escopo para minimizar duplicação (subtópicos ou tipos de fonte distintos para cada um)
  3. Agregação — juntar os resultados estruturados e montar a entrada do próximo estágio
  4. Seleção dinâmica — decidir quais subagents invocar com base na complexidade da query. Pergunta simples não precisa do pipeline completo; rotear sempre pelo pipeline inteiro é desperdício

Os papéis 2 e 4 aparecem juntos na prova como problema de custo e qualidade: pergunta de um fato só rodando busca, análise, síntese e relatório; subagents em paralelo recebendo o tópico inteiro e devolvendo as mesmas fontes. As duas correções moram no coordinator — avaliar a query antes de delegar e dar a cada subagent um subtópico ou tipo de fonte distinto. Regra de bolso: o coordinator dimensiona o trabalho: só os subagents que a query exige, e nenhum escopo repetido entre eles.

O risco clássico: decomposição estreita demais

É a questão oficial sobre orquestração (adaptada na Q1 abaixo). O sintoma: todos os subagents completam com sucesso, o relatório final é coerente — mas cobre só uma fatia do tópico. Nos logs, o coordinator quebrou um tema amplo em subtarefas de um nicho só. Os subagents executaram corretamente o escopo que receberam; o problema é o que foi atribuído. A causa raiz mora na decomposição do coordinator, e é lá que se corrige (ex.: instruir o coordinator a enumerar primeiro as dimensões do tópico antes de delegar, e conferir cobertura).

Loops de refinamento iterativo

O coordinator não é "dispara e esquece". O padrão maduro é um iterative refinement loop:

  1. Coordinator avalia a saída da síntese procurando gaps de cobertura
  2. Re-delega aos subagents de busca/análise com queries direcionadas aos gaps
  3. Re-invocar a síntese com os novos achados
  4. Repete até a cobertura ser suficiente

2. Spawning: Task tool, allowedTools e AgentDefinition (TS 1.3)

O mecanismo de spawn de subagents é a Task tool. Detalhe que derruba candidato: para o coordinator conseguir invocar subagents, o allowedTools dele precisa incluir "Task". Sem isso, o coordinator simplesmente não tem como delegar — e o sintoma em produção é um sistema "multi-agent" onde o coordinator tenta fazer tudo sozinho.

// Coordinator
const coordinator = {
  allowedTools: ["Task", "Read", "Grep"],   // "Task" é OBRIGATÓRIO para spawnar subagents
  systemPrompt: `Você coordena uma equipe de pesquisa. Analise a query,
    enumere as dimensões do tópico, delegue subtarefas distintas aos subagents
    disponíveis e avalie a síntese final quanto a gaps de cobertura.`
};

Cada tipo de subagent é declarado numa AgentDefinition, com três elementos que a prova cita por nome:

// AgentDefinition de um subagent especializado
const webSearcher = {
  description: "Busca fontes na web sobre um subtópico específico e retorna achados estruturados com URLs",
  prompt: "Você é um pesquisador web. Cubra APENAS o subtópico recebido no prompt...",   // o system prompt do subagent
  tools: ["WebSearch", "WebFetch"]   // tool restrictions: só as tools do papel dele
};
  • description — é como o coordinator decide qual subagent chamar (equivalente à tool description da aula sobre tools)
  • prompt (o system prompt do subagent) — define o papel, o escopo e o formato de saída do subagent
  • tool restrictions — cada subagent recebe só as tools do papel dele (um agent de síntese com acesso a web search vai tentar pesquisar em vez de sintetizar — misuse cross-role)

A description escolhe; quem restringe são as tools e o system prompt. A description diz ao coordinator quando usar aquele subagent — ela não limita o que o subagent pode fazer. Se um subagent só pode trabalhar com os documentos que recebe, isso se garante na lista de tools dele (só leitura de documentos) e no system prompt (papel e formato de saída), e não escrevendo "não use a web" na description. Regra de bolso: description = critério de seleção; tools + system prompt = limite do papel.

🧭 Prova × produto atual (documentação do Claude Code conferida em 20/10/2026)
  • Task → Agent. Na versão 2.1.63 do Claude Code, a Task tool passou a se chamar Agent; referências Task(...) em settings e definições de agente continuam valendo como alias. O guia e a prova dizem "Task".
  • allowedTools no Agent SDK atual só auto-aprova as tools listadas — não limita o conjunto. Quem limita é a opção tools (ou disallowedTools com o nome puro da tool). No guia, allowedTools é a lista que precisa conter "Task".
  • AgentDefinition sem o campo tools herda todas as tools disponíveis para subagents. Para limitar o papel, declare a lista explicitamente — coerente com a regra de bolso acima.
Na prova, responda como o guia: o allowedTools do coordinator precisa incluir "Task".

Diagnóstico: subagent mal configurado

O objetivo oficial pede que você diagnostique spawning mal configurado. São três classes de causa, e cada uma tem um sintoma próprio. Ler o sintoma antes das alternativas resolve a questão:

SintomaCausaCorreção
O coordinator não delega nada e faz tudo sozinho, com qualquer subagentpermissão de tool faltando"Task" no allowedTools do coordinator (no produto atual, Agent)
Os outros subagents funcionam, mas um deles nunca é chamado; ele não aparece na lista de agentes disponíveiswiring coordinator→subagent ausenteregistrar a AgentDefinition na opção agents do coordinator; escrever a definição sem passá-la não basta
O coordinator chama o subagent errado, ou alterna entre dois para a mesma tarefadescription vaga ou sobrepostadescriptions específicas e sem sobreposição: o que cada um faz e quando usar
O subagent certo é chamado, mas sai do papel (o sintetizador começa a pesquisar na web)tools não restritasdeclarar tools com só as do papel; sem o campo, ele herda todas as tools disponíveis para subagents

Na AgentDefinition, os campos obrigatórios são description e prompt; tools é opcional, e é justamente por ser opcional que a omissão passa despercebida. Regra de bolso: subagent que nunca é chamado → permissão (se nenhum é chamado) ou wiring (se só ele falta); chamado na hora errada → description; chamado na hora certa mas fazendo outra coisa → tools e system prompt.

3. Contexto isolado: subagents NÃO herdam histórico

Esta é a regra mais testada do TS 1.3: subagents operam com contexto isolado. Eles não herdam automaticamente o histórico da conversa do coordinator nem compartilham memória entre invocações. Tudo que um subagent precisa saber tem que ir explicitamente no prompt da Task call.

Consequência prática: quando o agent de síntese precisa dos achados da busca web e da análise de documentos, o coordinator coloca esses achados completos no prompt dele:

// Coordinator montando o prompt do subagent de síntese
const synthesisPrompt = `
Tópico original: ${userQuery}

ACHADOS DA BUSCA WEB (completos):
${JSON.stringify(webFindings, null, 2)}

ANÁLISE DOS DOCUMENTOS (completa):
${JSON.stringify(docAnalysis, null, 2)}

Sintetize um relatório preservando a atribuição de cada claim à sua fonte.`;

Se o subagent de síntese "esquece" o que a busca encontrou, a causa raiz não é o subagent — é o coordinator que não passou o contexto. E reinvocar "o mesmo" subagent esperando que ele lembre da invocação anterior não funciona: não há memória compartilhada entre invocações.

Formatos estruturados: separar conteúdo de metadados

Ao passar contexto entre agents, use estruturas que separam o conteúdo dos metadados (URL da fonte, nome do documento, número da página, data). É o que preserva a atribuição na síntese final:

{
  "claim": "Adoção de IA generativa em estúdios de jogos cresceu 40% em 2025",
  "evidence": "trecho literal do texto...",
  "source_url": "https://exemplo.com/relatorio-2025",
  "document_name": "Game Industry Report 2025",
  "page": 14,
  "published": "2025-11-02"
}

Achados passados como prosa solta ("a pesquisa diz que...") perdem o mapeamento claim→fonte na primeira sumarização. Estrutura preserva; prosa dilui. (Esse tema volta com força no Domínio 5, provenance.)

4. Subagents em paralelo: múltiplos Task calls numa única resposta

Para paralelizar, o coordinator emite múltiplas chamadas da Task tool na mesma resposta — não em turnos separados. Uma resposta com 3 blocos tool_use de Task dispara 3 subagents concorrentes; três turnos sequenciais com 1 Task cada os serializa. Partições de escopo independentes (subtópicos distintos, tipos de fonte distintos) são o caso ideal: rodam em paralelo, minimizam duplicação e reduzem a latência total.

// Resposta do coordinator: 3 Task calls NO MESMO turno → paralelas
[
  { "type": "tool_use", "name": "Task", "input": { "subagent": "web_searcher",
      "prompt": "Pesquise o subtópico: impacto da automação na indústria musical..." } },
  { "type": "tool_use", "name": "Task", "input": { "subagent": "web_searcher",
      "prompt": "Pesquise o subtópico: impacto da automação na produção cinematográfica..." } },
  { "type": "tool_use", "name": "Task", "input": { "subagent": "doc_analyzer",
      "prompt": "Analise os papers anexos sobre automação no mercado editorial..." } }
]

Paralelo só para o que é independente

Só saem na mesma resposta as subtarefas que não dependem umas das outras. Se a subtarefa D usa o resultado de A, B e C, ela vai num turno seguinte, com esses resultados colocados explicitamente no prompt dela — o subagent não "vê" o que os outros acharam (contexto isolado). Disparar a dependente junto com as outras só faz ela começar sem material; deixar que ela chame os outros subagents direto quebra o hub-and-spoke. Regra de bolso: independentes na mesma resposta; dependentes no turno seguinte, com os resultados no prompt.

Qual padrão de orquestração escolher

O objetivo oficial pede para escolher entre três estruturas pelo que o sistema precisa garantir: cobertura da pesquisa, latência e confiabilidade. Elas se combinam (um coordinator pode disparar workers em paralelo), mas cada uma otimiza uma coisa:

PadrãoCoberturaLatênciaConfiabilidadeEscolha quando
coordinator-workera maior: o coordinator decompõe, acha gaps e re-delegamédia a alta: há turnos extras do coordinatorerro centralizado e observável no hubo escopo não é conhecido de antemão e a cobertura importa
parallel executiondepende da partição: escopos distintos, sem sobreposiçãoa menor: as subtarefas rodam ao mesmo tempouma falha não pode derrubar as outras; resultado parcial vem anotadoas subtarefas são independentes e o prazo aperta
sequential pipelinefixa, definida no desenhoa maior: soma dos estágiosa mais previsível: ordem garantida e cada estágio testável; erro de um estágio chega ao seguinte se não for validadocada estágio precisa da saída do anterior e o processo tem de ser sempre o mesmo

Regra de bolso: escopo aberto → coordinator-worker; subtarefas independentes com pressa → paralelo; estágios dependentes que não podem ser pulados → pipeline. O caso oposto também vale: pipeline fixo para pesquisa aberta perde cobertura, e coordinator dinâmico para um processo que exige sempre os mesmos passos pode pular um deles.

Prompts do coordinator: metas, não procedimentos

Último ponto do blueprint: escreva prompts de coordinator que especificam objetivos de pesquisa e critérios de qualidade ("cubra todos os setores relevantes; toda claim precisa de fonte"), não instruções procedurais passo a passo ("primeiro chame X, depois Y"). Instrução procedural engessa os subagents e mata a adaptabilidade — justamente a vantagem de ter um modelo decidindo. A receita quebra no primeiro caso que ela não previu (outra fonte, outro formato), e acrescentar ramos ou fallbacks só adia a próxima quebra. O coordinator não perde visibilidade com isso: os resultados continuam voltando estruturados por ele. Regra de bolso: diga o que e com que qualidade, não como. E lembre: fork_session existe para explorar abordagens divergentes a partir de uma baseline de análise compartilhada (aprofundado na aula de sessões).

⚠️ Pegadinha do dia

Questões do tipo "todos os subagents rodaram com sucesso, mas o resultado final está incompleto/errado". Os distratores sempre culpam um subagent específico ("o search agent precisa de queries melhores", "o synthesis agent filtrou fontes"). Se o enunciado diz que cada subagent executou bem dentro do escopo recebido, a causa raiz está no coordinator — decomposição estreita, contexto não passado, ou seleção errada de subagents. Regra de bolso: subagent executa o escopo que recebe; escopo errado é problema de quem delegou, não de quem executou.

Um briefing regulatório semanal segue sempre os mesmos passos: coletar os documentos da semana, extrair os números, verificar cada número contra o documento de origem e escrever o briefing.
