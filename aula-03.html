Aula 03 — Enforcement, hooks e gerenciamento de sessões

Domínio 1 · Agentic Architecture & Orchestration (27%) Task Statements 1.4 – 1.7 ~60 min
🎯 Objetivo do dia. Aprender a transformar regras de negócio em garantias determinísticas via hooks (PreToolUse para bloquear, PostToolUse para normalizar) e prerequisite gates (nunca só via prompt quando a regra é determinística e checável em código — identidade antes de operação financeira, limite de valor, ordem obrigatória de etapas), montar handoffs estruturados para humanos, escolher entre prompt chaining e decomposição dinâmica, e gerenciar sessões com --resume, fork_session e recomeços com resumo estruturado.

1. Enforcement programático vs prompt-based (TS 1.4)

Esta é a regra central da aula e uma das mais cobradas da prova inteira:

Regra de ouro: quando uma regra de negócio exige compliance determinístico (verificação de identidade antes de operação financeira, limite de valor, ordem obrigatória de etapas), instrução no prompt tem taxa de falha não-zero — por melhor que seja o prompt, o modelo é probabilístico. Enforcement programático (hooks, prerequisite gates) é determinístico: a tool simplesmente não executa.

O sintoma clássico na prova: "em X% dos casos o agente pula a etapa A e chama a tool B diretamente". O candidato fraco propõe reforçar o system prompt ou adicionar few-shot examples — isso reduz a taxa de erro, mas não a elimina. A resposta certa implementa um prerequisite gate:

# Prerequisite gate: tools downstream bloqueadas até o pré-requisito
state = {"verified_customer_id": None}

def guard(tool_name, tool_input):
    if tool_name in ("lookup_order", "process_refund"):
        if state["verified_customer_id"] is None:
            return block("get_customer must return a verified customer ID first")
    return allow()

Note o desenho: o gate bloqueia lookup_order e process_refund até que get_customer tenha retornado um customer ID verificado. Não é o modelo que "decide obedecer" — é o seu código que torna a violação impossível.

Handoff estruturado para humanos

Outro padrão do TS 1.4: quando o agente escala para um atendente humano no meio do processo, o humano não tem acesso ao transcript da conversa. Mandar "resuma a conversa" gera handoff fraco. O handoff correto é um protocolo estruturado com campos fixos:

  • customer ID (verificado, não o nome declarado)
  • root cause — o que a investigação já concluiu
  • valor envolvido (ex.: refund amount)
  • ação recomendada — o próximo passo que o humano deve executar/aprovar

Trecho da conversa, transcript inteiro ou "resuma o que aconteceu" obrigam o atendente a reler e refazer o diagnóstico; score de prioridade ou autoconfiança do modelo não dizem o que fazer. Regra de bolso: o humano tem que conseguir agir sem reler nada — campos fixos com a conclusão e o próximo passo.

Pedido com vários assuntos (multi-concern)

"Meu pedido atrasou, quero trocar o endereço de entrega e tem uma cobrança duplicada." Tratar só o primeiro assunto e encerrar derruba a resolução no primeiro contato. O padrão do TS 1.4:

  1. Decompor a mensagem em itens distintos
  2. Investigar cada item em paralelo, usando o contexto compartilhado (o mesmo cliente verificado, os mesmos dados de conta) — em vez de um fluxo serial que mistura estados
  3. Sintetizar uma resolução unificada: uma resposta que fecha todos os itens

Escalar "porque tem muita coisa" não é saída: complexidade não é gatilho de escalonamento (os gatilhos são pedido explícito de humano, lacuna de política e falta de progresso). Regra de bolso: vários assuntos → itens investigados em paralelo com o mesmo contexto → uma resposta só.

2. Hooks do Agent SDK (TS 1.5)

Hooks são pontos de interceptação no ciclo de vida da tool call. A prova cobra dois usos:

2.1 PostToolUse — normalizar dados heterogêneos

Cenário: seu agente consome várias MCP tools e cada uma devolve dados num formato diferente — uma retorna timestamps Unix (1712345678), outra ISO 8601 (2024-04-05T14:21:18Z), outra códigos numéricos de status (3 em vez de "shipped"). Se você joga isso cru no modelo, ele precisa gastar raciocínio (e errar) fazendo parsing. Solução: um hook PostToolUse intercepta o tool result antes de o modelo processá-lo e normaliza para um formato canônico:

def post_tool_use(tool_name, tool_result):
    if "created_at" in tool_result:
        tool_result["created_at"] = to_iso8601(tool_result["created_at"])
    if isinstance(tool_result.get("status"), int):
        tool_result["status"] = STATUS_MAP[tool_result["status"]]
    return tool_result   # modelo recebe dados já normalizados

Alternativa errada que aparece como distrator: "ensinar no prompt que timestamps Unix devem ser convertidos" — de novo, probabilístico. A normalização é transformação mecânica; faça-a mecanicamente.

2.2 PreToolUse — bloquear violação de política

Cenário: a política diz que reembolsos acima de $500 exigem aprovação humana. A garantia correta é um hook que intercepta a chamada antes da execução, bloqueia a violação e redireciona para o workflow alternativo (escalação humana). No Agent SDK esse hook se chama PreToolUse: ele bloqueia com permissionDecision: "deny", e o permissionDecisionReason diz ao modelo por que a chamada foi negada e qual caminho seguir:

async def pre_tool_use(input_data, tool_use_id, context):
    if input_data["tool_name"].endswith("process_refund") and input_data["tool_input"]["amount"] > 500:
        return {"hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason":
                "Refund exceeds the $500 policy threshold: call escalate_to_human instead."}}
    return {}   # sem objeção: a chamada segue

A ordem importa: PreToolUse roda antes da execução e serve para impedir; PostToolUse roda depois e serve para transformar o resultado (2.1). Regra de bolso: para impedir uma ação, PreToolUse; para normalizar o que a tool devolveu, PostToolUse. Bloquear em PostToolUse chega tarde, porque o reembolso já saiu.

A frase-chave do guide: "choosing hooks over prompt-based enforcement when business rules require guaranteed compliance". Distrator clássico: "adicionar ao system prompt que refunds acima de $500 devem ser escalados" — funciona 95% das vezes, e os 5% restantes viram prejuízo financeiro.

3. Decomposição de tarefas: chaining vs dinâmica (TS 1.6)

Duas estratégias, e a prova testa se você sabe quando usar cada uma:

EstratégiaQuando usarExemplo canônico
Prompt chaining (pipeline sequencial fixo) Workflow previsível, com etapas conhecidas de antemão e múltiplos aspectos a revisar Code review: analisar cada arquivo individualmente → depois um pass de integração cross-file
Decomposição dinâmica adaptativa Investigação aberta, onde os próximos passos dependem do que se descobre "Adicionar testes a um codebase legado": mapear estrutura → identificar áreas de alto impacto → plano priorizado que se adapta conforme dependências surgem

O padrão de code review merece destaque porque cai muito: revisar um PR gigante "de uma vez" causa attention dilution — o modelo perde foco em meio a dezenas de arquivos e deixa passar bugs. A arquitetura correta:

  1. Pass local por arquivo: cada arquivo é revisado isoladamente, com atenção total
  2. Pass de integração cross-file: um pass separado analisa como os arquivos interagem (assinaturas quebradas, contratos mudados, efeitos colaterais entre módulos)

O pass cross-file existe porque bugs de integração não são visíveis olhando arquivo por arquivo — mas tentar pegar os dois tipos de bug num único pass dilui a atenção e piora os dois. Separação de concerns aplicada a review.

Os passes também podem se dividir por tipo de problema (segurança, lógica de negócio, design de API), cada um com prompt e few-shot próprios. É outro sintoma: não é volume de arquivos, são critérios competindo no mesmo prompt, e ganhar recall num tipo custa recall noutro. Detalhes na aula 11 (TS 4.6).

4. Sessões: resume, fork e recomeço (TS 1.7)

Claude Code persiste sessões nomeadas. Três operações que a prova cobra:

4.1 --resume <session-name>

Continua uma conversa anterior específica — ex.: uma investigação nomeada que atravessa vários dias de trabalho (claude --resume investigacao-checkout). Use quando o contexto anterior ainda é majoritariamente válido.

Detalhe que cai na prova: se arquivos foram modificados desde a sessão original, informe o agente sobre as mudanças específicas ao retomar ("os arquivos X e Y mudaram desde ontem; re-analise-os"). Isso permite re-análise direcionada em vez de re-exploração completa — e evita que o agente raciocine sobre tool results velhos que já não refletem o disco.

4.2 fork_session

Cria ramificações independentes a partir de uma baseline de análise compartilhada. Caso de uso: você já fez a análise do codebase uma vez e quer explorar duas abordagens divergentes — ex.: comparar duas estratégias de teste ou dois planos de refatoração — sem que uma contamine o contexto da outra. O fork herda a baseline; daí em diante, cada branch evolui isolado.

4.3 Nova sessão com resumo estruturado > retomar com tool results velhos

Quando o contexto antigo está stale (tool results de dias atrás, codebase mudou muito, a investigação tomou outro rumo), retomar a sessão injeta lixo no contexto e o modelo raciocina sobre dados desatualizados. A prática mais confiável: iniciar uma sessão nova injetando um resumo estruturado das conclusões relevantes da sessão anterior. Você preserva o conhecimento sem carregar os artefatos podres. Regra de decisão:

  • Contexto anterior ainda válido → --resume (e avise das mudanças pontuais em arquivos)
  • Tool results stale / codebase mudou muito → sessão nova + resumo estruturado
  • Quer explorar caminhos divergentes da mesma baseline → fork_session

⚠️ Pegadinha do dia

O distrator número 1 deste bloco é o remendo cosmético via prompt: o stem descreve uma violação de regra de negócio em produção (etapa pulada, refund acima do limite) e as opções oferecem "fortalecer o system prompt", "adicionar few-shot examples", "deixar a instrução mais enfática". Tudo isso é probabilístico. A resposta certa é sempre a que move a regra para código determinístico (hook, prerequisite gate, interceptação). Regra de bolso: regra de negócio determinística (checável em código: etapa obrigatória, limite de valor) com consequência financeira ou de compliance não pode morar no prompt — exige enforcement programático. Decisão de julgamento (quando escalar, qual tool escolher) é outra coisa: corrige-se primeiro com critérios explícitos + few-shot no prompt (questão 3 oficial, aula 12) — hook não sabe o que é exceção de política.
