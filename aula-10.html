Aula 10 — Structured output: tool_use, JSON schemas e validação-retry

Domínio 4 · Prompt Engineering & Structured Output (20%) ~60 min
🎯 Objetivo do dia. Dominar os Task Statements 4.3 e 4.4: por que tool_use com JSON schema é a forma mais confiável de obter saída estruturada (e o que ele não garante), como desenhar schemas que não induzem o modelo a fabricar dados, e como montar o loop de validação → retry com feedback de erro — incluindo saber quando retry é inútil.

1. Por que tool_use + JSON schema (Task Statement 4.3)

O jeito ingênuo de extrair dados estruturados é pedir no prompt "responda APENAS com JSON válido" e fazer json.loads() na saída de texto. Em produção isso quebra: o modelo embeleza o JSON com markdown (```json), adiciona frase antes ("Aqui está a extração:"), solta trailing comma. Cada quebra é uma exceção no seu pipeline. (Saída cortada por max_tokens é outro problema: tool_use não resolve, porque o bloco tool_use também pode vir incompleto, com stop_reason: "max_tokens" — a correção é aumentar max_tokens ou dividir a tarefa.)

A abordagem mais confiável — e a resposta padrão da prova para esse sintoma — é definir uma tool de extração cujo input_schema é o seu JSON schema. O modelo preenche os parâmetros da tool e a API devolve um bloco tool_use com o input já estruturado e garantidamente conforme o schema. Erros de sintaxe JSON desaparecem por construção — não porque o prompt ficou mais bonito, mas porque a estrutura é imposta pela camada de tool use.

tools = [{
  "name": "extract_invoice",
  "description": "Extract structured data from an invoice document.",
  "strict": True,                       # produto atual: garante input exatamente conforme o schema
  "input_schema": {
    "type": "object",
    "additionalProperties": False,
    "properties": {
      "invoice_number": {"type": "string"},
      "vendor": {"type": "string"},
      "currency": {"type": "string", "enum": ["BRL", "USD", "EUR", "other"]},
      "currency_other_detail": {"type": "string"},
      "stated_total": {"type": ["number", "null"]},
      "calculated_total": {"type": ["number", "null"]},
      "conflict_detected": {"type": "boolean"},
      "line_items": {
        "type": "array",
        "items": {"type": "object", "additionalProperties": False, "properties": {
          "description": {"type": "string"},
          "amount": {"type": "number"}
        }, "required": ["description", "amount"]}
      }
    },
    "required": ["invoice_number", "stated_total", "calculated_total", "conflict_detected", "line_items"]
  }
}]

resp = client.messages.create(
    model=..., messages=[{"role": "user", "content": document}],
    tools=tools,
    tool_choice={"type": "tool", "name": "extract_invoice"}   # forced
)
data = next(b.input for b in resp.content if b.type == "tool_use")

tool_choice no contexto de extração

  • "auto" (default): o modelo pode devolver texto em vez de chamar a tool. Inaceitável quando você exige saída estruturada — é a porta de entrada do bug "às vezes vem prosa".
  • "any": o modelo deve chamar uma tool, mas escolhe qual. É a escolha certa quando existem vários schemas de extração (nota fiscal, contrato, recibo) e o tipo do documento é desconhecido — garante structured output sem hard-codar o tipo.
  • {"type": "tool", "name": "extract_metadata"} (forced): o modelo deve chamar exatamente essa tool. Use quando uma extração específica precisa rodar antes de etapas de enriquecimento, ou quando só existe um schema possível.
🧭 Prova × produto atual (referência da API Claude conferida em 20/10/2026)
  • Input exatamente conforme o schema é garantia de strict: true na definição da tool (com additionalProperties: false no schema). Sem ele, o modelo segue o schema, mas pode omitir campo ou errar tipo. O guia fala em "strict JSON schemas".
  • tool_choice "any" e forçado devolvem erro 400 no Claude Opus 5.5, Sonnet 5.5, Fable 5.1 e Mythos 5.1 (o Opus 5, o Sonnet 5 e modelos anteriores aceitam). Nesses modelos usa-se "auto" + instrução nomeando a tool + strict: true, ou saída estruturada (output_config.format) quando o objetivo é só receber JSON.
Na prova, responda como o guia: "any" quando o tipo do documento é desconhecido; forced para garantir que uma extração específica rode antes.

2. Schema estrito NÃO impede erros semânticos

Distinção que a prova cobra sem dó: tool_use com schema elimina erros de sintaxe (JSON malformado, campo faltando, tipo errado). Ele não elimina erros semânticos: os line items extraídos podem não somar o total da nota, um valor pode cair no campo errado (data de vencimento no campo de data de emissão), tudo perfeitamente válido contra o schema.

A solução proporcional não é "schema ainda mais estrito" — é validação semântica no seu código depois da extração, combinada com self-correction embutida no próprio schema e retry com feedback (os dois na seção 4). Schema garante forma; validação garante sentido.

3. Schema design: não induza o modelo a fabricar

Campo required é uma ordem: "preencha isso". Se a informação não existe no documento, o modelo tende a inventar um valor plausível para satisfazer o schema — o pior tipo de erro, porque passa silenciosamente por toda validação estrutural. As ferramentas de design:

  • optional / nullable: se o documento de origem pode não conter a informação, deixe o campo opcional ou aceite null. null honesto é infinitamente melhor que valor fabricado.
  • enum com "unclear": para campos categóricos em que o documento pode ser ambíguo, ofereça a saída explícita "unclear" em vez de forçar um palpite.
  • enum com "other" + campo detail string: categorias extensíveis. O modelo nunca precisa entortar um caso novo para caber num enum fechado — marca "other" e explica em category_other_detail.
  • regras de normalização no prompt: formato de data, separador decimal, moeda variam entre documentos. Schema estrito + instruções de normalização no prompt trabalham juntos — um cuida da estrutura, o outro do formato. Não confunda com o hook PostToolUse da aula 03 — veja a pegadinha extra no fim da seção 5.

4. Validação, retry e self-correction (Task Statement 4.4)

Retry-with-error-feedback

Quando a validação semântica falha, não basta "chamar de novo". O retry eficaz reenvia na mesma conversa: o documento original + a extração que falhou + o erro de validação específico. O modelo então corrige o próprio trabalho com informação concreta do que está errado.

data = extract(document)                      # 1ª passada
errors = validate(data)                       # ex.: ["line_items sum 412.00 != stated_total 421.00"]
if errors:
    messages += [
      {"role": "assistant", "content": [failed_tool_use_block]},
      {"role": "user", "content": [{
          "type": "tool_result", "tool_use_id": failed_tool_use_block.id, "is_error": True,
          "content": "Validation failed on your extraction:\n- " + "\n- ".join(errors) +
                     "\nRe-read the document and correct ONLY the inconsistent fields."}]}
    ]
    data = extract_again(messages)            # retry COM feedback específico

Os limites do retry

Retry funciona para erros de formato e estrutura — o dado estava lá, o modelo leu errado. Retry é inútil quando a informação simplesmente não existe no documento fornecido (ex.: o número do pedido só consta num e-mail externo que nunca entrou no contexto). Repetir a chamada com feedback cada vez mais enfático só aumenta o custo e a pressão para o modelo fabricar. A correção é no input: trazer a fonte que falta para o contexto — ou aceitar o null honesto.

Self-correction embutida no schema

Em vez de confiar cegamente no total impresso, peça calculated_total (soma dos line items) junto de stated_total (total impresso) e um booleano conflict_detected. O próprio modelo confronta as duas fontes a cada extração, e documentos com dados inconsistentes na origem saem flagados — em vez de "corrigidos" em silêncio.

detected_pattern: o feedback loop além da extração

Em ferramentas de análise (ex.: code review automatizado), desenvolvedores dispensam findings. Sem dados estruturados, você nunca sabe por quê. Adicione um campo detected_pattern a cada finding registrando qual construção de código disparou o alerta. Com isso você analisa sistematicamente quais padrões são mais dispensados e refina a tool — transformando dismiss em sinal de melhoria, não em ruído. Repare que isso não é um score de confiança: a confiança diz quanto o modelo acredita no finding; o detected_pattern diz o que o disparou — e é isso que permite reescrever o critério com base em dado.

Regra de bolso: finding descartado é dado. Registre o padrão que o disparou, agrupe os descartes por ele e só então mexa no prompt.

⚠️ Pegadinha do dia

Sintoma: "o pipeline de extração quebra com JSON malformado / campos faltando / texto antes do JSON". Os distratores sempre oferecem remendo de prompt ("reescreva a instrução pedindo JSON válido, em letras maiúsculas") ou parser mais tolerante. Quando a exigência é garantia determinística de estrutura, a resposta certa é mover a estrutura para a camada de tool_use com input_schema — e, se o modelo ainda puder fugir para texto, ajustar o tool_choice ("any" ou forced). Regra de bolso: prompt pede; schema garante. Garantia de formato não se negocia em linguagem natural.

⚠️ Pegadinha extra — normalizar no hook ou no prompt?

As duas respostas aparecem na prova, e as duas estão certas — cada uma no seu contexto. A pergunta que decide é de onde vem o valor:

  • De um resultado de tool (uma MCP tool devolve timestamp Unix, outra ISO 8601, outra status numérico) → hook PostToolUse que normaliza antes de o modelo ver (TS 1.5, aula 03). É transformação mecânica e determinística sobre um dado que já chega correto.
  • Da leitura que o próprio modelo faz do documento (datas como 03/04/26, valores como "1.250,00" ou "1 250 €") → regras de normalização no prompt, junto do schema estrito, com exemplos dos casos ambíguos (TS 4.3). O erro nasce na leitura; só instrução e exemplo ensinam a ler.

Os distratores dos dois lados: pattern mais estrito no schema (garante a forma, não o sentido) e retry (corrige formato inválido, mas não corrige dia e mês trocados nem separador mal lido, porque o valor errado continua válido). Regra de bolso: valor que vem de tool se normaliza no hook; valor que o modelo extrai se normaliza no prompt, com exemplos.

Questão 1 · múltipla escolha Structured Data Extraction
Your invoice extraction pipeline prompts the model to "respond with valid JSON only" and parses the text output. In production, roughly 8% of runs crash the parser: markdown fences around the JSON, a sentence before the object, or a trailing comma after the last field. What is the root-cause fix?
Seu pipeline de extração de notas fiscais pede no prompt "responda apenas com JSON válido" e faz parse do texto. Em produção, ~8% das execuções quebram o parser: markdown em volta do JSON, uma frase antes do objeto, ou uma vírgula sobrando depois do último campo. Qual é a correção de causa raiz?
Gabarito: C. Erro de sintaxe JSON se resolve por construção: com tool_use + input_schema, a estrutura é garantida pela camada de tool use e o input já vem parseado. A é remendo cosmético — prompt não gera garantia determinística. B empilha heurística frágil em cima do problema em vez de eliminá-lo. D trata o sintoma com retry cego e caro: a falha não é intermitente, é consequência de parsear texto livre. Domínio 4 · TS 4.3 — Saída estruturada com tool use e JSON schema

Questão 3 · múltipla escolha Structured Data Extraction
After migrating invoice extraction to tool use with a strict JSON schema, syntax errors dropped to zero — but finance reports that in some extractions the line items do not add up to the extracted total. What is the most proportional response?

Questão 4 · múltipla resposta (select TWO / marque DUAS) Structured Data Extraction
Your contract extraction marks every field as required and uses a closed enum for clause_type. Reviewers found that when a contract lacks a termination clause, the model invents a plausible termination date, and when a clause is ambiguous or matches no enum value, it forces the closest category. Which TWO schema design changes directly address this fabrication?
Sua extração de contratos marca todos os campos como required e usa um enum fechado para clause_type. Revisores descobriram que, quando o contrato não tem cláusula de rescisão, o modelo inventa uma data plausível, e quando uma cláusula é ambígua ou não bate com nenhum valor do enum, ele força a categoria mais próxima. Quais DUAS mudanças de design de schema atacam diretamente essa fabricação?
Gabarito: B e E. Campo required é uma ordem de preenchimento: se a informação pode não existir, optional/nullable (B) dá ao modelo a saída honesta (null); e, no clause_type, enums com "unclear"/"other"+detail (E) absorvem ambiguidade e casos novos sem forçar a categoria mais próxima. A é remendo de prompt contra uma pressão estrutural criada pelo próprio schema — instrução não vence campo obrigatório. C é o distrator clássico: temperatura não tem relação com fabricação induzida por schema. D valida só a forma: uma data inventada e bem-formada passa no format: date.
