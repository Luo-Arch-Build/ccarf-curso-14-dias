Slash commands: project scope versus user scope (TS 3.2)

Slash commands: escopo de projeto versus escopo de usuário (TS 3.2)
  • A custom slash command is a Markdown file whose content becomes the prompt when you type /command-name.
  • The architectural decision the exam tests is where the file lives, and the answer depends on who should receive it.
  • .claude/commands/ inside the repository is project scope: it goes into version control, so every developer who clones or pulls receives the command automatically.
  • Project scope is the place for any standardized team workflow, such as /review, /deploy-check or /new-endpoint.
  • ~/.claude/commands/ in the user's home directory is personal scope: it does not enter the repo, is not shared, and holds your individual shortcuts.
  • When the stem says available to every developer when they clone, or shared with the team, the answer is .claude/commands/ in the repository, and any option with ~/ is wrong because it does not pass through version control.
  • Um custom slash command é um arquivo Markdown cujo conteúdo vira o prompt quando você digita /nome-do-comando.
  • A decisão arquitetural que a prova cobra é onde o arquivo mora, e a resposta depende de quem deve recebê-lo.
  • .claude/commands/ dentro do repositório é escopo de projeto: vai para o controle de versão, então todo dev que clona ou dá pull recebe o comando automaticamente.
  • O escopo de projeto é o lugar de qualquer workflow padronizado do time, como /review, /deploy-check ou /novo-endpoint.
  • ~/.claude/commands/ no home do usuário é escopo pessoal: não entra no repo, não é compartilhado e guarda os seus atalhos individuais.
  • Quando o stem diz disponível para todo dev ao clonar, ou compartilhado com o time, a resposta é .claude/commands/ no repositório, e qualquer opção com ~/ está errada porque não passa pelo controle de versão.

Skills: SKILL.md with frontmatter (TS 3.2)

Skills: SKILL.md com frontmatter (TS 3.2)
  • A skill is a package of specialized instructions that Claude loads on demand, when the task calls for it, instead of occupying context all the time.
  • A project skill lives in .claude/skills/<name>/SKILL.md, and a personal skill lives in ~/.claude/skills/<name>/SKILL.md.
  • SKILL.md has YAML frontmatter, and the exam names three of its fields: context, allowed-tools and argument-hint.
  • context: fork runs the skill in an isolated sub-agent, so verbose output such as a whole-codebase analysis stays out of the main conversation and only the result or summary comes back.
  • context: fork is the skill equivalent of the Explore subagent.
  • allowed-tools restricts which tools the skill can use during execution; the classic exam case is limiting a skill to file reads and writes to prevent destructive actions.
  • argument-hint is the text shown when a developer invokes the skill without its required parameters, reminding them what to pass.
  • Uma skill é um pacote de instruções especializadas que o Claude carrega sob demanda, quando a tarefa pede, em vez de ocupar contexto o tempo todo.
  • Uma skill de projeto vive em .claude/skills/<nome>/SKILL.md, e uma skill pessoal vive em ~/.claude/skills/<nome>/SKILL.md.
  • O SKILL.md tem frontmatter YAML, e a prova cobra nominalmente três campos: context, allowed-tools e argument-hint.
  • context: fork roda a skill num sub-agent isolado, então a saída verbosa, como a análise de um codebase inteiro, fica fora da conversa principal e só o resultado ou o resumo volta.
  • context: fork é o equivalente em skill do Explore subagent.
  • allowed-tools restringe quais tools a skill pode usar durante a execução; o caso clássico da prova é limitar uma skill a leitura e escrita de arquivos para impedir ações destrutivas.
  • argument-hint é o texto exibido quando um dev invoca a skill sem os parâmetros obrigatórios, lembrando o que passar.

Exam versus current product (docs checked on 2026-10-22)

Prova versus produto atual (documentação conferida em 22/10/2026)

  • To remove tools while a skill is active, the current product has a separate field, disallowed-tools.
  • With context: fork, the skill runs in a subagent that does not see your conversation history and returns a summary when it finishes, which is the isolation the guide describes.
  • On the exam, answer as the guide does: allowed-tools restricts the skill's tools.

Personal variant, and Skill versus CLAUDE.md

Variante pessoal, e Skill versus CLAUDE.md
  • To customize a project skill only for yourself, create a variant in ~/.claude/skills/ under a different name, for example analise-codebase-luo.
  • A different name does not collide with the team's skill and does not change your colleagues' behavior.
  • Editing the repo's skill would change everyone's workflow, and committing a personal preference is exactly the anti-pattern the exam tests.
  • A skill loads on demand when the task calls for it, while CLAUDE.md is always loaded in every session.
  • A skill suits task-specific workflows such as analysis, migration or release; CLAUDE.md suits universal project standards such as style, conventions and never-do-X rules.
  • A skill costs context only when used, while CLAUDE.md costs context permanently, and letting it grow too much pollutes everything.
  • When the stem says a standard that applies to all project code, the answer is CLAUDE.md; when it says a workflow that runs occasionally, with parameters and large output, the answer is a skill, probably with context: fork.
  • A skill can be invoked by name or loaded by Claude by relevance, but either way it stays on demand: loaded by relevance does not make it always-on guidance like CLAUDE.md.
  • Para customizar uma skill do projeto só para você, crie uma variante em ~/.claude/skills/ com um nome diferente, por exemplo analise-codebase-luo.
  • Um nome diferente não colide com a skill do time e não altera o comportamento dos colegas.
  • Editar a skill do repo mudaria o workflow de todo mundo, e commitar uma preferência pessoal é exatamente o anti-padrão que a prova testa.
  • Uma skill carrega sob demanda quando a tarefa pede, enquanto o CLAUDE.md é sempre carregado em toda sessão.
  • A skill serve a workflows específicos de uma tarefa, como análise, migração ou release; o CLAUDE.md serve a padrões universais do projeto, como estilo, convenções e regras de nunca fazer X.
  • Uma skill só custa contexto quando usada, enquanto o CLAUDE.md custa contexto permanentemente, e deixá-lo crescer demais polui tudo.
  • Quando o stem diz um padrão que vale para todo código do projeto, a resposta é CLAUDE.md; quando diz um workflow que roda às vezes, com parâmetros e saída grande, a resposta é uma skill, provavelmente com context: fork.
  • Uma skill pode ser invocada pelo nome ou carregada pelo Claude por relevância, mas nas duas formas continua sob demanda: carregada por relevância não vira orientação always-on como o CLAUDE.md.

Quick map: which mechanism for each need

Mapa rápido: qual mecanismo para cada necessidade
  • The exam likes to list several needs and ask for the mechanism of each; the criterion is always when the guidance applies and who should receive it.
  • A standard for every developer in every session goes in the project CLAUDE.md, which is always loaded and versioned.
  • A convention for one file type spread across the repo goes in .claude/rules/ with a paths glob, covered in Lesson 6.
  • A workflow that runs occasionally, with parameters or large output, is a skill in .claude/skills/, with context: fork if it is verbose.
  • A standardized prompt the team fires by name is a slash command in .claude/commands/.
  • A shortcut that is only yours goes in ~/.claude/commands/ or ~/.claude/skills/, under its own name.
  • Something that must always happen without exception, such as running the linter after every edit, is a hook configured in settings.json: programmatic enforcement, not instruction, the logic of TS 1.5 from Lesson 3.
  • Changing the session's overall autonomy and approval, such as stopping approval prompts for every edit or only planning, is the session's permission mode, enumerated in Lesson 8.
  • Always blocking a command or a file, such as the .env file or the secrets/ folder, is a deny rule under permissions in the project's versioned .claude/settings.json.
  • A prova gosta de listar várias necessidades e pedir o mecanismo de cada uma; o critério é sempre quando a orientação se aplica e quem deve recebê-la.
  • Um padrão para todo dev em toda sessão vai no CLAUDE.md do projeto, sempre carregado e versionado.
  • Uma convenção de um tipo de arquivo espalhado pelo repo vai em .claude/rules/ com glob em paths, tema da Aula 06.
  • Um workflow que roda às vezes, com parâmetros ou saída grande, é uma skill em .claude/skills/, com context: fork se for verboso.
  • Um prompt padronizado que o time dispara pelo nome é um slash command em .claude/commands/.
  • Um atalho só seu vai em ~/.claude/commands/ ou ~/.claude/skills/, com nome próprio.
  • Algo que precisa acontecer sempre, sem exceção, como rodar o linter depois de toda edição, é um hook configurado em settings.json: enforcement programático, não instrução, a lógica do TS 1.5 da Aula 03.
  • Mudar a autonomia e a aprovação gerais da sessão, como parar de pedir aprovação a cada edição ou só planejar, é o permission mode da sessão, que a Aula 08 enumera.
  • Bloquear sempre um comando ou um arquivo, como o .env ou a pasta secrets/, é uma regra deny em permissions no .claude/settings.json do projeto, versionado.

Permission rules: allow, ask and deny in settings (TS 3.2)

Regras de permissão: allow, ask e deny nos settings (TS 3.2)
  • Permission rules live under permissions, with allow, ask and deny lists, in the settings files.
  • Claude Code itself applies permission rules before the tool runs, so they do not depend on the model following an instruction.
  • A deny rule in the project's .claude/settings.json, such as Read(**/.env), Read(./secrets/**) or Bash(terraform apply:*), applies to the whole team.
  • Rules are evaluated in the order deny, then ask, then allow, and among rules deny always wins.
  • Read(./.env) matches only the .env in the current directory, while Read(**/.env) matches all of them.
  • File precedence from strongest to weakest is: managed organization policy, command-line arguments, .claude/settings.local.json (personal, outside git), .claude/settings.json (project, versioned), and ~/.claude/settings.json (user).
  • Lists such as permissions.allow are combined across files instead of overriding each other, which is why a personal allow does not reopen what a project deny closed.
  • For a rule that the whole organization must follow and nobody can remove, there is the managed level.
  • As regras de permissão ficam em permissions, com as listas allow, ask e deny, nos arquivos de settings.
  • O próprio Claude Code aplica as regras de permissão antes de a tool rodar, então elas não dependem de o modelo seguir uma instrução.
  • Uma regra deny no .claude/settings.json do projeto, como Read(**/.env), Read(./secrets/**) ou Bash(terraform apply:*), vale para o time inteiro.
  • As regras são avaliadas na ordem deny, depois ask, depois allow, e entre regras o deny sempre ganha.
  • Read(./.env) casa só com o .env do diretório atual, enquanto Read(**/.env) casa com todos.
  • A precedência dos arquivos, do mais forte ao mais fraco, é: política managed da organização, argumentos de linha de comando, .claude/settings.local.json (pessoal, fora do git), .claude/settings.json (projeto, versionado) e ~/.claude/settings.json (usuário).
  • Listas como permissions.allow se combinam entre os arquivos em vez de se sobrescreverem, e por isso um allow pessoal não reabre o que um deny do projeto fechou.
  • Para uma regra que a organização inteira deve seguir e que ninguém pode remover, existe o nível managed.

Hook, deny rule and permission mode are three different controls

Hook, regra deny e permission mode são três controles diferentes
  • Hooks are also configured in the settings files, and additionally in plugins and in the frontmatter of skills and subagents.
  • A hook executes something on an event; a deny rule prevents a tool call.
  • A permission mode is not a per-target rule: it changes the session's overall autonomy and approval, meaning what runs without asking.
  • An allow, ask or deny rule decides about a specific target: a tool, a command or a path.
  • Permission mode, permission rules and hooks act together, and none of them replaces another; the modes are covered in Lesson 8.
  • Rule of thumb: always loaded is CLAUDE.md; depends on the file is a rule with glob; on demand is a skill or command; a guarantee is code, never text: what must happen is a hook, and what must never happen is a deny rule.
  • A deny rule blocks without looking at context, so when a prohibition depends on a condition, such as only in production or only above a value, it becomes a hook with logic.
  • A PreToolUse hook can inspect a command and its target, deny production calls, and leave development calls to the other permission rules; not being denied by that hook does not mean automatic permission.
  • The deny rule's reach covers the native tools and the commands Claude Code recognizes, such as cat, head and redirections, not a script that opens the file on its own; for that, use the sandbox.
  • Style and naming are guidance in CLAUDE.md or a rule, and they only become a command hook when there is an executable criterion, such as a formatter that runs or a validator that blocks.
  • With an executable criterion, the formatter runs after a successful edit in a PostToolUse hook, and the validator blocks the action before it runs in a PreToolUse hook.
  • Hooks também se configuram nos arquivos de settings e, além disso, em plugins e no frontmatter de skills e subagents.
  • Um hook executa algo num evento; uma regra deny impede uma tool call.
  • Um permission mode não é regra por alvo: ele muda a autonomia e a aprovação gerais da sessão, ou seja, o que roda sem perguntar.
  • Uma regra allow, ask ou deny decide sobre um alvo específico: uma tool, um comando ou um caminho.
  • Permission mode, regras de permissão e hooks atuam juntos, e um não substitui o outro; os modos estão na Aula 08.
  • Regra de bolso: sempre carregado é CLAUDE.md; depende do arquivo é rule com glob; sob demanda é skill ou comando; garantia é código, nunca texto: o que tem de acontecer é hook, e o que nunca pode acontecer é regra deny.
  • Uma regra deny bloqueia sem olhar contexto, então quando uma proibição depende de uma condição, como só em produção ou só acima de um valor, ela vira hook com lógica.
  • Um hook PreToolUse pode inspecionar um comando e seu destino, negar chamadas de produção e deixar as de desenvolvimento para as demais regras de permissão; não ser negado por esse hook não equivale a permissão automática.
  • O alcance da regra deny cobre as tools nativas e os comandos que o Claude Code reconhece, como cat, head e redirecionamentos, e não um script que abre o arquivo por conta própria; para isso, use o sandbox.
  • Estilo e nomes são orientação em CLAUDE.md ou rule, e só viram hook de comando quando existe um critério executável, como um formatter que roda ou um validador que bloqueia.
  • Com um critério executável, o formatter roda depois de uma edição bem-sucedida num hook PostToolUse, e o validador bloqueia a ação antes de ela rodar num hook PreToolUse.

Direct execution, plan mode and multi-phase workflow (TS 3.4)

Execução direta, plan mode e workflow multifásico (TS 3.4)
  • Direct execution, plan mode and a multi-phase workflow are three different choices, not three names for the same cycle.
  • Choose direct execution when the change is simple, well understood and well scoped, such as a bug with a clear stack trace, a validation in one function or renaming a variable.
  • In direct execution Claude edits and runs within the permissions; review can be manual, edit by edit or command by command, and supervision does not turn the task into plan mode.
  • Choose plan mode when the design is still uncertain: multiple valid approaches, unknown dependencies, an architectural decision or a change across many files.
  • In plan mode Claude reads and explores without modifying files, produces a plan, and implements only after that plan is approved.
  • Plan approval controls Claude's transition from planning to implementation; it does not authorize production or deployment.
  • Choose a multi-phase workflow when the process requires separate phases with independent owners or checks, such as discovery, approval, implementation, verification and release.
  • In a multi-phase workflow each phase delivers an artifact, such as a report, a plan, a diff or test evidence, passed on by a handoff, and human or programmatic gates decide whether the next phase can start.
  • A single plan-then-execute cycle is a useful combination of modes but is not enough to define a multi-phase workflow.
  • A multi-phase workflow can contain plan mode in its design phase, as long as it has other explicit phases, artifacts, handoffs and gates.
  • Planning before an uncertain change prevents costly rework, but planning an already understood three-line fix is process over-engineering.
  • The exam penalizes both planning everything and starting directly on a task whose complexity is already declared.
  • Execução direta, plan mode e workflow multifásico são três escolhas diferentes, não três nomes para o mesmo ciclo.
  • Escolha execução direta quando a mudança é simples, bem compreendida e bem delimitada, como um bug com stack trace claro, uma validação numa função ou renomear uma variável.
  • Na execução direta o Claude edita e executa dentro das permissions; a revisão pode ser manual, edição por edição ou comando por comando, e supervisão não transforma a tarefa em plan mode.
  • Escolha plan mode quando o desenho ainda é incerto: múltiplas abordagens válidas, dependências desconhecidas, uma decisão arquitetural ou uma mudança em muitos arquivos.
  • No plan mode o Claude lê e explora sem modificar arquivos, produz um plano e só implementa depois da aprovação desse plano.
  • A aprovação do plano controla a transição do Claude do planejamento para a implementação; ela não autoriza produção nem deploy.
  • Escolha workflow multifásico quando o processo exige fases separadas, com responsáveis ou verificações independentes, como discovery, aprovação, implementação, verificação e release.
  • No workflow multifásico cada fase entrega um artefato, como relatório, plano, diff ou evidência de testes, passado adiante por um handoff, e gates humanos ou programáticos decidem se a fase seguinte pode começar.
  • Um único ciclo plano e execução é uma combinação útil de modos, mas não basta para definir um workflow multifásico.
  • Um workflow multifásico pode conter plan mode na fase de desenho, desde que tenha outras fases explícitas, artefatos, handoffs e gates.
  • Planejar antes de uma mudança incerta previne retrabalho caro, mas planejar uma correção de três linhas já compreendida é over-engineering de processo.
  • A prova penaliza tanto planejar tudo quanto começar direto uma tarefa cuja complexidade já está declarada.

Plan approval is not a production or deployment gate

Aprovação do plano não é gate de produção ou deploy
  • Plan approval answers whether Claude can leave planning and implement this proposal.
  • A requirement from the data owner, a change advisory board or a release policy answers a different question: whether this change can reach the environment or produce an external effect.
  • That authorization needs the corresponding external process, such as an approval recorded in the change system, environment protection, a CI/CD gate or programmatic validation; plan mode alone does not provide it.
  • Risk and human review shape the design of the controls but do not create an automatic mode rule.
  • A simple edit can use direct execution supervised by ask permissions and manual review; a high-risk change may require plan mode and external gates; a process with independent approval, implementation and verification calls for a multi-phase workflow.
  • Risk or human approval, on their own, do not make plan mode sufficient.
  • claude -p --permission-mode plan can produce a plan without editing files, but a second headless run does not automatically inherit the session or the approved plan.
  • To implement the same proposal headless, explicitly resume the corresponding session or give the new run the approved plan artifact and the needed context; production and deployment approvals remain separate gates even then.
  • A aprovação do plano responde se o Claude pode sair do planejamento e implementar esta proposta.
  • Uma exigência do dono do dado, do change advisory board ou de uma política de release responde outra pergunta: se esta mudança pode chegar ao ambiente ou produzir efeito externo.
  • Essa autorização precisa do processo externo correspondente, como aprovação registrada no sistema de mudanças, proteção de ambiente, gate de CI/CD ou validação programática; plan mode, sozinho, não a fornece.
  • Risco e revisão humana influenciam o desenho dos controles, mas não criam uma regra automática de modo.
  • Uma edição simples pode usar execução direta supervisionada por permissions ask e revisão manual; uma mudança de alto risco pode exigir plan mode e gates externos; um processo com aprovação, implementação e verificação independentes pede um workflow multifásico.
  • Risco ou aprovação humana, isoladamente, não tornam plan mode suficiente.
  • claude -p --permission-mode plan pode produzir um plano sem editar arquivos, mas uma segunda execução headless não herda automaticamente a sessão nem o plano aprovado.
  • Para implementar a mesma proposta em headless, retome explicitamente a sessão correspondente ou forneça à nova execução o artefato do plano aprovado e o contexto necessário; mesmo assim, aprovações de produção e deploy continuam sendo gates separados.

Explore subagent: protecting the context

Explore subagent: protegendo o contexto
  • Discovery phases, such as finding where a function is used or mapping all callers, generate huge output: dozens of files read, greps and listings.
  • If that output enters the main conversation, the context window runs out before the implementation phase.
  • The Explore subagent runs the verbose search in an isolated context and returns only the summary, the same logic as context: fork in skills.
  • Lesson 12, section 3, returns to subagents for verbose exploration in large codebases.
  • In a multi-phase workflow, that summary can be the discovery artifact handed to the design phase, the approved plan becomes another artifact received by implementation, and an independent verification produces its own evidence before the release gate.
  • The Explore subagent protects the context but does not replace those handoffs and gates.
  • For a large task with an uncertain design, plan mode followed by direct execution can be enough; if the requirement also calls for a discovery report, formal approval, implementation and independent verification, the answer becomes a multi-phase workflow, possibly using plan mode in one phase.
  • Neither the size of the prompt nor the number of steps mentioned decides the architecture: look for explicit artifacts, handoffs and gates.
  • Fases de discovery, como achar onde uma função é usada ou mapear todos os callers, geram saída enorme: dezenas de arquivos lidos, greps e listagens.
  • Se essa saída entra na conversa principal, a janela de contexto acaba antes da fase de implementação.
  • O Explore subagent faz a busca verbosa num contexto isolado e devolve só o resumo, a mesma lógica do context: fork das skills.
  • A Aula 12, seção 3, retoma os subagents para exploração verbosa em codebases grandes.
  • Num workflow multifásico, esse resumo pode ser o artefato de discovery entregue à fase de desenho, o plano aprovado vira outro artefato recebido pela implementação, e uma verificação independente produz evidências próprias antes do gate de release.
  • O Explore subagent protege o contexto, mas não substitui esses handoffs e gates.
  • Para uma tarefa grande de desenho incerto, plan mode seguido de execução direta pode bastar; se o requisito também exigir relatório de discovery, aprovação formal, implementação e verificação independente, a resposta passa a ser workflow multifásico, possivelmente com plan mode numa das fases.
  • Nem o tamanho do prompt nem a quantidade de etapas mencionadas decidem a arquitetura: procure artefatos, handoffs e gates explícitos.

Trap of the day

Pegadinha do dia
  • Wrong scope: something available to the whole team goes in the versioned repo, not in ~/.claude/.
  • Mode as a reflex: plan mode for every task is over-engineering, and starting directly on an already declared complexity is also an error.
  • False multi-phase: a plan followed by execution is not enough; look for phases with artifacts, handoffs and gates.
  • Approval or invisible memory: approving Claude's plan does not authorize production or deployment, and a new headless run does not inherit the plan without resuming the session or receiving the artifact.
  • Wrong text or wrong block: an instruction does not guarantee enforcement; use deny for an unconditional prohibition and a hook with logic when the decision depends on context.
  • Rule of thumb: shared means the versioned repo; a simple change means direct execution, even with per-edit review; an uncertain design means plan mode; a process with independent handoffs and gates means a multi-phase workflow.
  • Escopo errado: algo disponível para o time inteiro vai no repo versionado, não em ~/.claude/.
  • Modo como reflexo: plan mode para toda tarefa é over-engineering, e começar direto uma complexidade já declarada também é erro.
  • Falso multifásico: um plano seguido de execução não basta; procure fases com artefatos, handoffs e gates.
  • Aprovação ou memória invisível: aprovar o plano do Claude não autoriza produção nem deploy, e uma nova execução headless não herda o plano sem retomar a sessão ou receber o artefato.
  • Texto ou bloqueio errado: instrução não garante enforcement; use deny para proibição incondicional e hook com lógica quando a decisão depender do contexto.
  • Regra de bolso: compartilhado é o repo versionado; mudança simples é execução direta, mesmo com revisão por edição; desenho incerto é plan mode; processo com handoffs e gates independentes é workflow multifásico.
