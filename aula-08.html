1. Refinamento iterativo (Task Statement 3.5)

1.1 Exemplos concretos de input/output > descrição em prosa

Quando você descreve uma transformação em prosa ("normalize os nomes de forma consistente") e o Claude interpreta de um jeito diferente a cada execução, o problema não é o modelo — é que prosa é ambígua por natureza. A correção canônica: fornecer 2–3 exemplos concretos de input/output mostrando exatamente a transformação esperada.

# Em vez de: "formate os registros de forma limpa"
# Forneça pares input → output:

Input:  { "nome": "MARIA  silva", "tel": "(11)98765-4321", "vip": "S" }
Output: { "name": "Maria Silva", "phone": "+5511987654321", "tier": "vip" }

Input:  { "nome": "joão PEREIRA", "tel": null, "vip": "N" }
Output: { "name": "João Pereira", "phone": null, "tier": "standard" }

Exemplos resolvem de uma vez o que parágrafos de instrução não resolvem: capitalização, tratamento de null, formato de telefone, nome de campos. A prova adora o contraste "prosa cada vez mais detalhada" (distrator) vs "2-3 concrete input/output examples" (resposta).

1.2 Test-driven iteration: testes primeiro, falhas como guia

O fluxo que o Exam Guide descreve: escreva a suíte de testes antes (comportamento esperado, edge cases, requisitos de performance), peça a implementação, e itere compartilhando as falhas dos testes — não re-descrevendo o requisito em prosa.

  1. Escreva os testes cobrindo o comportamento esperado e os edge cases (ex.: valores null num script de migração)
  2. Peça a implementação ao Claude
  3. Rode os testes; cole a saída exata da falha no chat: input, output esperado vs obtido
  4. Repita até a suíte passar

A falha do teste é uma especificação não-ambígua do bug: ela tem input concreto, expectativa concreta e resultado concreto. É a versão automatizada do item 1.1. Para corrigir um edge case específico, forneça o caso de teste com input de exemplo e output esperado — não "trate melhor os nulos".

Regra de bolso: quando a descrição em prosa de um mesmo requisito gera versões que não convergem (corrige um caso, quebra outro), pare de descrever — escreva o teste que o define e compartilhe a falha. Se são problemas distintos cujas correções interagem, é o caso do 1.4: uma única mensagem detalhada com todos.

1.3 Interview pattern: Claude pergunta antes de implementar

Em domínios que você não domina (ex.: estratégias de cache, modos de falha de um protocolo), você não sabe quais decisões de design importam — e o Claude, instruído a "implementar X", vai escolher defaults silenciosamente. O interview pattern inverte a direção: antes de codar, peça para o Claude entrevistar você com perguntas sobre o problema.

Before implementing, interview me: ask questions about requirements,
constraints, and failure modes I may not have considered. Only start
coding after I answer.

Isso faz emergir considerações que você não antecipou (invalidação de cache, comportamento em falha parcial, concorrência) antes de virarem retrabalho. Distrator clássico: "escreva um prompt mais detalhado" — você não consegue detalhar o que não sabe que existe.

Regra de bolso: domínio desconhecido → o Claude pergunta antes de codar; transformação conhecida mas descrita de forma ambígua → exemplos de input/output (1.1).

1.4 Issues interagentes numa única mensagem vs independentes em sequência

Quando há vários problemas para corrigir, a decisão é:

  • Fixes que interagem (ex.: refresh de token e timeout de sessão — mexer num muda o comportamento do outro) → uma única mensagem detalhada descrevendo todos. O Claude precisa raciocinar sobre a interação e produzir uma solução coerente. Corrigir em sequência gera o ciclo "consertei A, quebrei B; consertei B, quebrei A".
  • Issues independentes (bug no parser + typo no log) → iteração sequencial normal, um de cada vez, sem custo.

A pergunta de prova é sempre: os fixes se tocam? Se sim, mesma mensagem.

2. Claude Code em CI/CD (Task Statement 3.6)

2.1 Modo não-interativo: a flag -p / --print

Num pipeline não há humano para digitar. Se você rodar claude "Analyze this pull request" num job de CI, o processo trava esperando input interativo e o job morre por timeout. A solução documentada é a flag -p (ou --print): processa o prompt, imprime o resultado em stdout e encerra.

# Trava no CI (modo interativo):
claude "Analyze this pull request for security issues"

# Correto para pipelines:
claude -p "Analyze this pull request for security issues"

2.2 Output estruturado: --output-format json + --json-schema

Texto livre não é parseável pelo pipeline. Para postar findings automaticamente como comentários inline no PR, o output precisa ser JSON válido num schema conhecido:

claude -p "Review this diff for bugs" \
  --output-format json \
  --json-schema '{"type":"object","properties":{
    "findings":{"type":"array","items":{"type":"object","properties":{
      "file":{"type":"string"},"line":{"type":"integer"},
      "severity":{"type":"string"},"issue":{"type":"string"},
      "suggested_fix":{"type":"string"}},"required":["file","line","severity","issue"]}}}}'

Com isso o job pode fazer jq/parse determinístico e postar cada finding na linha certa do PR — sem regex em cima de texto livre. O resultado validado fica em structured_output.

O schema restringe a estrutura quando uma saída estruturada válida é produzida, mas não garante sua presença: se a execução terminar sem uma saída válida, o campo structured_output pode estar ausente. Antes de consumir findings, o pipeline deve verificar o resultado e a presença/o tipo desse campo e falhar explicitamente se a verificação não passar. Ausência de output não significa "zero findings".

Note a divisão de trabalho: --output-format json faz a saída ser JSON parseável; o --json-schema é o que fixa a estrutura (chaves, tipos, campos obrigatórios) do structured output válido. Descrever o formato no prompt reduz a variação, mas continua probabilístico. Regra de bolso: se um script consome a saída, a estrutura é imposta por schema, não pedida em texto; a presença do resultado é verificada pelo pipeline.

2.3 Permission modes, limites de turnos e de custo, tools do revisor

O -p resolve o travamento, mas não diz o que o Claude pode fazer sem ninguém olhando. O Exam Guide não lista essas flags, mas os objetivos oficiais da prova (a lista que vem no score report) cobram "non-interactive flags, permission modes, and cost and turn limits that prevent runaway executions" e "restrict unnecessary tool access". Trate como matéria de prova. São três travas, uma por pergunta:

PerguntaFlagO que faz
O que roda sem aprovação?--permission-modeAceita default, acceptEdits, plan, auto, dontAsk e bypassPermissions.
Até onde ele pode ir?--max-turns · --max-budget-usdLimite de turnos agênticos (ao atingir, encerra com erro) e de gasto estimado no cliente. O orçamento ajuda a conter runaway, mas não é um teto contábil rígido: a estimativa pode divergir da fatura. Os dois só no modo -p.
Quais tools existem?--tools · --disallowedTools--tools restringe as tools nativas disponíveis; --disallowedTools remove tools da sessão, inclusive MCP quando especificado.

Os modos que importam no CI:

  • dontAsk: nega automaticamente toda tool call que exigiria aprovação. Ações que já não pedem permissão continuam rodando, como leituras no diretório de trabalho e comandos read-only; regras allow, --allowedTools e aprovações por PreToolUse também têm efeito próprio, e um mod instalado ainda pode aprovar algumas chamadas. Portanto, dontAsk evita espera por prompt, mas não é uma allowlist absoluta: tools e regras continuam definindo a superfície disponível.
  • bypassPermissions: pula as checagens de permissão. Só em ambiente isolado (container, VM, dev container sem internet). Num runner com segredos e acesso à rede, é o distrator.
  • plan: o Claude analisa e propõe, sem editar. Também funciona com -p (ver aula 07).
  • acceptEdits: aceita sem perguntar edições de arquivo e comandos comuns de sistema de arquivos (mkdir, mv, rm…) dentro do diretório de trabalho. Serve para o job que gera código, não para o revisor.
# Revisor de PR: nativas só de leitura, sem tools MCP, sem prompt e com limites
claude -p "Review this diff against the standards in CLAUDE.md" \
  --permission-mode dontAsk \
  --tools "Read,Grep,Glob" \
  --disallowedTools "mcp__*" \
  --max-turns 15 --max-budget-usd 2 \
  --output-format json --json-schema "$SCHEMA"

Cuidado com o nome parecido: --allowedTools não restringe. Ele só pré-aprova (as tools listadas rodam sem pedir permissão) e todas as outras continuam disponíveis. Quem tira tools é --tools ou --disallowedTools. Dois detalhes: --tools limita só as tools nativas; como este revisor não precisa de MCP, --disallowedTools "mcp__*" trata separadamente essas tools. E tirar só Edit e Write não basta se o Bash continua disponível — sed -i, mv e rm também mudam arquivos.

Regra de bolso: para um revisor sem tools de escrita, restrinja as nativas a --tools "Read,Grep,Glob" e trate o MCP (aqui, negando mcp__*); só com essa condição o conjunto de tools expostas é read-only. Isso não substitui isolamento do runner nem proteção de segredos. --allowedTools é para o caso oposto, deixar rodar sem perguntar uma tool que você quer que rode. Job que pode entrar em loop (corrigir até o teste passar) → --max-turns e --max-budget-usd; se o job começa a parar por limite antes de terminar o trabalho legítimo, o limite está apertado para a tarefa: ajuste-o ou divida a tarefa, não tire a trava.

2.4 As duas integrações oficiais de review

Além de chamar claude -p no seu próprio script, há duas integrações prontas, e são produtos diferentes:

  • GitHub Actions (anthropics/claude-code-action, instalada com /install-github-app ou manualmente): roda o Claude Code no seu workflow. Os padrões do projeto vêm do CLAUDE.md, que ele lê a cada execução; flags da CLI (tools, limites, modelo) vão no input claude_args.
  • Code Review gerenciado: a Anthropic revisa os PRs por você. O review é ajustado pelo CLAUDE.md e pelo REVIEW.md; o REVIEW.md é lido da branch base ou da default, nunca das mudanças do próprio PR (um PR não consegue afrouxar as regras que o revisam). Não faz push de commits: comenta no PR.

Regra de bolso: quer controlar o workflow, as flags e os limites → Action com claude_args; quer review pronto sem manter pipeline → Code Review, com as regras no REVIEW.md. Nos dois, as convenções do projeto moram em arquivo do repositório, não no prompt do job (2.5).

🧭 Prova × produto atual (documentação do Claude Code conferida em 29/10/2026)
  • Com --json-schema, um resultado válido vem no campo structured_output do JSON de saída (só no modo -p); se a execução não produzir saída válida, o campo pode não existir.
  • manual é aceito como alias de default em --permission-mode (v2.1.200+).
  • No Agent SDK, a parada por orçamento aparece como resultado com subtype error_max_budget_usd.
  • total_cost_usd e o orçamento de --max-budget-usd usam estimativas calculadas no cliente, que podem divergir da cobrança real.
Detalhes de produto: a prova cobra o papel de cada flag (seção 2.3), não esses nomes de campo.

2.5 CLAUDE.md no CI: descoberta normal × modo bare

Sem --bare, claude -p descobre e carrega configuração como uma sessão interativa: CLAUDE.md, auto memory, hooks, Skills, comandos, subagents, plugins e MCP servers do ambiente. Num runner, isso não é neutro: a documentação alerta que -p não mostra o diálogo de workspace trust nem aprovação por server. Não execute conteúdo de um repositório não confiável presumindo que o modo não-interativo o neutraliza.

Com --bare, a inicialização ignora essa descoberta automática, reduzindo variação entre máquinas e evitando hooks/plugins/MCP herdados. É o modo recomendado pela documentação para scripts e runners que precisam de comportamento reproduzível. O contexto necessário passa a ser explícito: por exemplo, --append-system-prompt-file "CLAUDE.md" para incluir as convenções revisadas do projeto e --mcp-config somente se um server realmente for necessário. Não confunda -p com --bare: o primeiro torna a execução não-interativa; o segundo controla a descoberta de configuração.

O CLAUDE.md continua sendo o mecanismo de contexto de projeto para padrões de teste, fixtures, critérios de review e o que é um teste valioso. Isso evita cópias divergentes das convenções no prompt de cada job. Sem --bare, ele é descoberto normalmente; com --bare, inclua-o deliberadamente pelo arquivo. Em ambos os casos, valide o resultado e não trate contexto como enforcement. Regra de bolso: convenções compartilhadas moram no CLAUDE.md; em CI reproduzível e com superfície mínima, use --bare e forneça esse contexto explicitamente.

2.6 Self-review bias: a sessão que gerou o código é pior revisora dele

A mesma sessão que escreveu o código já "decidiu" que aquela abordagem é correta — o contexto dela está contaminado pelo raciocínio que produziu o código. Resultado: review raso, tendência a aprovar as próprias escolhas. A correção arquitetural: revisar numa instância independente, que vê só o diff e os critérios de review, sem o histórico de geração. Em CI isso é natural: o job de review é uma invocação nova de claude -p, não a continuação da sessão do autor.

2.7 Re-rodando reviews após novos commits: só issues novos/não-resolvidos

Cenário clássico: o review roda a cada push. Sem cuidado, cada execução reposta os mesmos findings e o PR acumula comentários duplicados — devs passam a ignorar o bot. A solução: incluir os findings anteriores no contexto da nova execução e instruir explicitamente: report only new issues or previously reported issues that are still unaddressed.

claude -p "You previously reported these findings on this PR:
$(cat previous-findings.json)
Review the new commits. Report ONLY new issues or prior issues that
remain unaddressed. Do not repeat findings that were fixed." \
  --output-format json --json-schema "$SCHEMA"

O mesmo princípio vale para geração de testes: inclua os arquivos de teste existentes no contexto, para o Claude não sugerir cenários que a suíte já cobre.

2.8 Exercício construtivo: repare a invocação e o gate do pipeline

Um runner compartilhado, com rede e segredos, já gravou o diff em pr.diff. O review deve apenas ler e reportar; não deve editar nem usar MCP. Este job está inseguro e incompleto:

claude "Review pr.diff and fix every finding" \
  --permission-mode bypassPermissions \
  --allowedTools "Read,Grep,Glob" \
  --max-turns 40 \
  --output-format json --json-schema "$SCHEMA" |
jq -r '.structured_output.findings // []'

Reescreva a invocação e o consumo do resultado atendendo a todos os requisitos:

  • modo não-interativo com -p e permission mode que negue o que exigiria aprovação;
  • somente Read,Grep,Glob como tools nativas e nenhuma tool MCP;
  • --max-turns e --max-budget-usd para conter execução descontrolada;
  • JSON com schema de findings e uma verificação que falhe o job se houver erro ou se structured_output estiver ausente/inválido.

Justifique cada correção pelo problema que ela resolve. Não trate --allowedTools como restrição nem ausência de output como lista vazia.

Confira uma solução completa 
set -euo pipefail

SCHEMA='{"type":"object","properties":{"findings":{"type":"array","items":{"type":"object","properties":{"file":{"type":"string"},"line":{"type":"integer"},"severity":{"type":"string"},"issue":{"type":"string"},"suggested_fix":{"type":"string"}},"required":["file","line","severity","issue"],"additionalProperties":false}}},"required":["findings"],"additionalProperties":false}'

  1. -p executa uma vez e encerra, sem esperar input interativo. --bare impede a descoberta de hooks, Skills, plugins, MCP e outras configurações do host, e --append-system-prompt-file "CLAUDE.md" fornece deliberadamente as convenções revisadas que o bare não carrega automaticamente. O prompt também deixa de pedir correções: o papel deste job é reportar.
  2. dontAsk nega chamadas que cairiam em aprovação; não é, sozinho, uma allowlist. Por isso --tools reduz as nativas ao mínimo read-only. --disallowedTools "mcp__*" deixa explícita a política de nenhum MCP mesmo com --bare, e nenhum --mcp-config é fornecido. Não há allowedTools pré-aprovando ações desnecessárias.
  3. --max-turns 12 limita iterações; --max-budget-usd 1.50 interrompe com base no gasto estimado no cliente. É contenção de runaway, não garantia contábil do valor final da fatura.
  4. --output-format json produz o envelope parseável e --json-schema restringe o structured output válido. O jq -e exige sucesso e um objeto com findings array; se o campo estiver ausente ou a execução tiver erro, o job falha antes de publicar. Um array vazio legítimo continua sendo um resultado válido, diferente de campo ausente.

⚠️ Pegadinha do dia

Nas questões de CI/CD, os distratores são de dois tipos. O primeiro: features que não existem (CLAUDE_HEADLESS=true, --batch, --ci-mode) ou gambiarras de shell (< /dev/null, timeout 60 claude ...) que não resolvem a causa raiz. O segundo, mais traiçoeiro: flag real no papel errado — bypassPermissions num runner com segredos, --allowedTools para "restringir" o revisor, instrução no prompt no lugar de --max-turns. As flags documentadas que a prova cobra: -p/--print, --output-format json, --json-schema, --permission-mode, --max-turns, --max-budget-usd, --tools/--disallowedTools. Regra de bolso: flag ou variável de ambiente que não está na documentação do Claude Code é distrator; flag que existe só é resposta se faz o papel pedido — job trava esperando input → -p; estrutura da saída → --output-format json + --json-schema; ausência de structured_output → verificar e falhar; job sem humano que não pode pedir aprovação → dontAsk; loop ou gasto estimado sem limite → --max-turns/--max-budget-usd; revisor só leitura → restringir nativas e tratar MCP com --tools/--disallowedTools.
