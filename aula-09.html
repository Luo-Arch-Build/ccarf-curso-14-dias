Aula 09 — Critérios explícitos e few-shot prompting

Domínio 4 · Prompt Engineering & Structured Output (20%) ~60 min
🎯 Objetivo do dia. Dominar as duas técnicas de prompt que a prova mais cobra no Domínio 4: substituir instruções vagas ("be conservative") por critérios categóricos explícitos para derrubar falsos positivos — guardados como contexto persistente, que vale em todo review —, e usar few-shot prompting — 2 a 4 exemplos mirados em casos ambíguos, mostrando o raciocínio — para obter formato consistente e reduzir alucinação em extração.

1. Critérios explícitos > instruções vagas (Task Statement 4.1)

O cenário clássico da prova: seu review automatizado gera falsos positivos demais e o time começa a ignorar os comentários. A tentação é adicionar ao prompt algo como "be conservative" ou "only report high-confidence findings". Não funciona. Essas instruções são vagas — cada execução do modelo interpreta "conservador" e "alta confiança" de um jeito, e a precisão não melhora de forma mensurável.

O que funciona: critérios categóricos explícitos que dizem exatamente o que reportar e o que pular. Compare:

# ❌ Vago — a prova usa isso como DISTRATOR
"Check that comments are accurate. Be conservative and only report
 high-confidence findings."

# ✅ Categórico — define o que entra e o que sai
"Flag a comment ONLY when the behavior it claims contradicts the actual
 code behavior (e.g., comment says 'returns null on empty input' but the
 code throws). Do NOT report: wording style, missing docstrings, comment
 formatting, or comments that are merely incomplete but not wrong."

Note o padrão: o critério bom é testável — dado um achado, você consegue dizer objetivamente se ele entra ou não na categoria. "High-confidence" não é testável; "claimed behavior contradicts actual code behavior" é.

Falsos positivos corroem a confiança do time inteiro

Segundo ponto que a prova cobra: uma categoria com taxa alta de FP não prejudica só ela — ela mina a confiança dos desenvolvedores nas categorias precisas também. Dev que descarta 8 achados lixos de "performance" passa a descartar os achados reais de "security" por reflexo.

A jogada proporcional enquanto você melhora o prompt: desabilitar temporariamente a categoria com alto FP. É melhor rodar 3 categorias confiáveis do que 5 categorias das quais 2 ensinam o time a clicar em "dismiss" sem ler. Quando o prompt da categoria problemática estiver reescrito (com critérios explícitos + few-shot), reabilite.

Severidade: critérios + exemplos de código por nível

Classificação de severidade inconsistente (o mesmo bug vira critical num PR e minor em outro) se resolve do mesmo jeito: defina cada nível com um critério explícito e um exemplo de código concreto:

SEVERITY CRITERIA (report exactly one per finding):

- critical: data loss, security vulnerability, or crash in production paths.
  Example: user input concatenated into a SQL query without parameterization.

- major: incorrect behavior under realistic inputs, no data loss.
  Example: retry loop that double-charges the customer when the gateway
  times out, because the charge call is not idempotent.

- minor: maintainability issues with no behavioral impact.
  Example: duplicated date-parsing logic that could drift apart.

Sem os exemplos, "major" vs "minor" vira julgamento de humor do modelo. Com exemplos, a classificação fica consistente entre PRs e entre desenvolvedores.

Onde os critérios moram: contexto persistente

Critério bom escrito no prompt de uma execução vale só para ela: no próximo PR, no próximo job ou no rerun de um colega, o mesmo falso positivo volta. O objetivo oficial da prova pede o contrário: "supplying project-specific conventions, accepted patterns, and exclusion criteria as persistent context applied on every review". São três tipos de conteúdo:

  • Convenções do projeto: como o time escreve código aqui (padrão de erros, nomes, camadas).
  • Padrões aceitos: o que parece problema mas é decisão do time (ex.: o catch amplo no adapter de pagamento é intencional e documentado; SQL cru é aceito no módulo de relatórios).
  • Critérios de exclusão: o que nunca reportar (código gerado em src/gen/, vendor/, estilo que o linter já cobre).

Onde guardar: no CLAUDE.md do projeto, que toda invocação do Claude Code carrega, inclusive no CI (aula 08, seção 2.5); em .claude/rules/ com glob quando o critério depende do tipo de arquivo (aula 06); no REVIEW.md quando o review é o Code Review gerenciado (aula 08, seção 2.4).

Regra de bolso: critério que vale para todo review → arquivo versionado no repo (CLAUDE.md, rule, REVIEW.md), nunca colado no prompt de cada execução. O caso oposto: critério que vale só para uma execução (ex.: "neste PR, ignore o módulo legado que vai ser apagado") fica no prompt daquela execução — persistir isso faria todo review futuro pular o módulo.

2. Few-shot prompting (Task Statement 4.2)

Quando instruções detalhadas sozinhas produzem saída inconsistente — formato variando, campos faltando, julgamento errático — a técnica mais eficaz é few-shot: incluir no prompt 2 a 4 exemplos completos de entrada → saída desejada. A prova trata isso quase como regra: instrução descreve; exemplo demonstra.

Como escolher os exemplos (é aqui que a prova pega)

  • Mire nos cenários ambíguos, não nos óbvios. Um exemplo de caso fácil já fixa o formato, mas ensina pouco sobre julgamento. O valor está em mostrar o que fazer quando duas ações parecem plausíveis (qual tool chamar num pedido ambíguo, se um padrão de código é issue real ou padrão aceitável do time).
  • Mostre o raciocínio de por que aquela ação foi escolhida em vez da alternativa plausível. É isso que permite ao modelo generalizar o julgamento para padrões novos, em vez de só "casar" com os casos que você listou.
  • Demonstre o formato exato da saída — ex.: location, issue, severity, suggested_fix. Formato demonstrado em exemplo é seguido com muito mais consistência do que formato descrito em prosa.
  • 2 a 4 exemplos bastam. Mais que isso gasta contexto e começa a overfitar nos casos listados.
## Example 1 (ambiguous tool choice — chosen action + reasoning)
Input: "Can you check why my order never arrived?"
Chosen action: lookup_order(order_id from context) → NOT escalate_to_human
Reasoning: the request is trackable with existing tools and involves no
policy exception; escalation would add wait time without adding capability.

## Example 2 (review finding — exact output format + reasoning)
Input: src/orders/retry.py, line 42 — on gateway timeout the loop calls
charge(order) again, with no idempotency key.
Output:
{
  "location": "src/orders/retry.py:42",
  "issue": "non-idempotent charge retried on timeout",
  "severity": "major",
  "suggested_fix": "pass an idempotency key derived from order_id"
}
Reasoning: major, not critical — wrong behavior under realistic inputs
(double charge) without data loss, security hole or crash.

Few-shot contra alucinação em extração

Em extração de dados (notas fiscais, papers, contratos), os documentos reais chegam em formatos variados: citações inline vs bibliografia, seção de metodologia vs detalhes embutidos no texto, medidas informais ("meia xícara", "cerca de 2 colheres"). Sem exemplos, o modelo tende a inventar valores para preencher campos ou retornar vazio/nulo quando o layout foge do esperado.

A correção é incluir few-shot mostrando a extração correta em cada variação de estrutura — inclusive o exemplo que demonstra "quando a informação não está no documento, retorne null, não fabrique". Isso reduz alucinação porque o modelo aprende, por demonstração, o comportamento esperado diante da ambiguidade do mundo real.

⚠️ Pegadinha do dia

O distrator favorito desse tema é o confidence score autorreportado cru: "peça ao modelo para dar nota de confiança de 1 a 10 em cada achado e só mostre os acima de 8". Parece engenhoso, mas a confiança autorreportada crua é mal calibrada — o agente pode estar confiante justamente nos casos difíceis em que erra; usada crua como filtro ou como gatilho de escalonamento, é distrator. Variantes do mesmo distrator: "be conservative", "só reporte achados de alta confiança", "treine um classificador separado" (over-engineering antes de tentar prompt). Regra de bolso: precisão se ganha com critérios categóricos testáveis + few-shot de casos ambíguos com raciocínio, não com filtro por confiança crua. Confiança autorreportada só vira sinal de roteamento para revisão humana depois de calibrada contra um conjunto rotulado (TS 4.6 e 5.5, aulas 11 e 13).
