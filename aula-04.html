Aula 04 — Design de tools: descrições, distribuição e tool_choice

Domínio 2 · Tool Design & MCP Integration (18%) ~60 min
🎯 Objetivo do dia. Dominar a regra de ouro do Task Statement 2.1: a descrição da tool é o mecanismo primário que o modelo usa para escolher qual tool chamar — e aprender a diagnosticar e corrigir misrouting causado por descrições mínimas ou sobrepostas. Depois, o Task Statement 2.3: distribuir tools entre agentes com scoped access (só as tools do papel de cada agente, least privilege) e escolher o tool_choice certo ("auto" vs "any" vs forced).

1. A descrição da tool é o mecanismo de seleção (TS 2.1)

Quando o modelo decide qual tool chamar, ele não executa código nem consulta um índice: ele lê as descrições que você declarou e raciocina sobre elas. Descrição é documentação que o modelo consome em tempo de decisão. Por isso o guide é direto: minimal descriptions lead to unreliable selection among similar tools.

Cenário clássico de prova: duas tools parecidas (get_customer e lookup_order), ambas com descrições de uma linha ("Retrieves customer information" / "Retrieves order details") e identificadores parecidos. Resultado: o usuário pergunta "check my order #12345" e o agente chama a tool errada. A correção de primeiro passo, barata e de alto impacto: expandir as descrições.

Anatomia de uma boa descrição

  • Propósito — o que a tool faz, em linguagem específica do domínio
  • Formatos de input — o que ela aceita (ex.: "order ID no formato ORD-XXXXX, não email nem CPF")
  • Exemplos de queries — frases de usuário que devem rotear para ela ("where is my package?")
  • Edge cases — o que acontece com ID inexistente, pedido antigo, múltiplos resultados
  • Fronteiras (boundaries) — quando usar esta tool versus a tool similar: "use para status de pedido; para dados cadastrais do cliente, use get_customer"
// ANTES — descrição mínima, seleção não confiável
{ "name": "lookup_order", "description": "Retrieves order details" }

// DEPOIS — propósito + input + exemplos + edge cases + fronteira
{ "name": "lookup_order",
  "description": "Looks up the status and contents of a customer order.
    Input: an order ID in the format ORD-XXXXX (not an email or customer ID).
    Use for queries like 'check my order #12345', 'where is my package?'.
    Returns 'not found' for unknown or archived (>2 years) orders.
    For customer profile data (name, address, plan), use get_customer instead." }

2. Overlap, renomeação, split — e o sequestro via system prompt

Descrições sobrepostas causam misrouting

Se analyze_content e analyze_document têm descrições quase idênticas, o modelo não tem como diferenciá-las — ele vai escolher de forma inconsistente, e o sintoma em produção é misrouting. As duas correções do guide:

  1. Renomear e especializar: analyze_content → extract_web_results, com descrição específica de web. O nome da tool também é sinal de seleção.
  2. Dividir a tool genérica: um analyze_document faz-tudo vira tools com contratos definidos de input/output — extract_data_points, summarize_content, verify_claim_against_source. Cada uma com propósito único e inconfundível.

System prompt keyword-sensitive sequestra a seleção

Descrições ótimas podem ser sobrescritas por instruções frágeis do system prompt. Exemplo ilustrativo (o guide enuncia só o princípio, sem exemplo): uma instrução tipo "for anything order-related, use lookup_order" faz o agente chamar lookup_order até quando o usuário escreve "in order to reset my password…". A instrução reage à keyword literal, não à intenção. O fix é revisar o system prompt e reescrever a instrução descrevendo intenção ("use lookup_order para perguntas sobre status de pedidos"), não palavras-chave. Nas questões, se o stem diz "descriptions are well written" e o agente ainda erra de forma sistemática numa keyword, suspeite do system prompt.

3. Distribuição de tools e tool_choice (TS 2.3)

Menos tools por agente = seleção melhor

Dar 18 tools a um agente degrada a confiabilidade da seleção: cada tool a mais aumenta a complexidade da decisão e a chance de overlap semântico. O guide ilustra com 18 tools em vez de 4–5, mas o que a prova cobra é o princípio — cada agente só com as tools do seu papel —, não uma cota numérica. Além disso, agentes com tools fora da especialização tendem a misusá-las (ex.: o synthesis agent tentando fazer web search sozinho).

  • Scoped tool access: cada subagente recebe apenas as tools do seu papel.
  • Substituir tools genéricas por versões restritas: trocar fetch_url (abre qualquer URL) por load_document, cujo handler valida se o destino é um documento permitido e rejeita o resto. A restrição determinística passa a morar no contrato executado da tool: o agente não consegue usá-la fora do papel dele, por mais que o raciocínio o leve para lá. Nome, descrição e input schema ajudam a orientar e validar a forma da chamada, mas, isoladamente, não impõem essa política semântica de destino. Regra de bolso: se um agente usa uma tool genérica fora da especialização dele, estreite a tool e faça o handler aplicar a restrição — não peça por favor no prompt.
  • Cross-role de alta frequência, com escopo: se o synthesis agent precisa checar fatos simples (datas, nomes, estatísticas) com frequência, dê a ele uma verify_fact escopada — e continue roteando verificações complexas para o web-search agent via coordinator. É o princípio do least privilege: só o necessário para o caso comum, sem abrir o arsenal inteiro.

tool_choice: auto vs any vs forced

// "auto" (default): o modelo PODE chamar tool ou responder com texto
tool_choice: {"type": "auto"}

// "any": o modelo É OBRIGADO a chamar alguma tool (sem resposta conversacional)
tool_choice: {"type": "any"}

// forced: o modelo É OBRIGADO a chamar ESTA tool específica
tool_choice: {"type": "tool", "name": "extract_metadata"}
  • Use "auto" quando a tool for opcional e uma resposta com o contexto já disponível também for aceitável.
  • Use "any" quando você precisa garantir uma chamada de tool, mas mais de uma tool disponível seria adequada — ex.: um importador pode chamar qualquer parser compatível, enquanto resposta em texto livre quebraria o pipeline.
  • Use forced quando a resposta daquele turno precisa solicitar uma tool específica — ex.: extract_metadata na primeira requisição. Os passos seguintes continuam dependendo de execução e validação pela aplicação.
  • Ponto-chave de prova: quando o requisito é garantir que o modelo emita um tool_use — para alguma tool ("any") ou uma específica naquele turno (forced) —, a solução é tool_choice, não frase imperativa no system prompt ("ALWAYS call a tool"), que continua probabilística. Já ordem obrigatória entre execuções de tools ao longo do workflow e regra de negócio (process_refund só depois de get_customer devolver um ID verificado; refund acima do limite) pedem um prerequisite gate no código da aplicação/orquestrador (aula 03, TS 1.4/1.5).

4. Client tools: da emissão do tool_use à ordem executada

Com client tools, o modelo solicita a chamada, mas quem executa o handler é a sua aplicação. Um tool_use não é uma execução concluída, e um tool_result não deve ser tratado como prova de sucesso sem validação.

  1. tool_use: a Messages API devolve um bloco com id, name e input. Com forced selection, essa resposta solicita a tool escolhida em vez de texto ou outra tool.
  2. Aplicação executa: seu código despacha o tool_use para o handler correspondente, captura exceções/timeout e normaliza o outcome. O modelo não executa esse código.
  3. tool_result: a aplicação preserva a mensagem assistant com o tool_use e acrescenta o resultado com o mesmo tool_use_id para a próxima requisição; falha pode ser indicada com is_error e/ou um outcome estruturado.
  4. Validação: antes de liberar a etapa seguinte, o orquestrador confere o status real do handler, o formato do resultado e os dados pré-requisitos de negócio — por exemplo, extração concluída e um document_id presente e válido.
  5. Próxima etapa: somente após esse gate o workflow marca a etapa como concluída e habilita/expõe enrich_document em um turno posterior.

Caminho de falha: exceção, timeout, is_error, resultado inválido ou document_id ausente mantêm o enrichment bloqueado. A aplicação devolve/registra o tool_result de falha quando couber e segue retry, recuperação ou escalonamento; ela só reavalia a liberação depois de uma nova execução válida. Não se deve avançar apenas porque o modelo emitiu a tool certa.

// Pseudocódigo: a próxima etapa começa bloqueada
state.enrichment_enabled = False
response = messages.create(...,
  tool_choice={"type": "tool", "name": "extract_metadata"})
call = require_tool_use(response, name="extract_metadata")
outcome = application.execute(call)       // exceções viram status="error"
messages.append_tool_result(call, outcome) // tool_use_id + content/is_error

if outcome.status != "success":
    return recover_or_retry(outcome)      // enrichment permanece bloqueado

metadata = outcome.data
if not valid_metadata(metadata) or not metadata.get("document_id"):
    return recover_or_retry("missing prerequisite: document_id")

state.metadata = metadata
state.enrichment_enabled = True
return run_enrichment_turn()              // só exposta depois do gate

Duas garantias diferentes: tool_choice controla a emissão da solicitação na resposta do modelo; o prerequisite gate garante a ordem efetivamente executada pelo workflow. Forced selection sozinha não prova sucesso nem impede que a aplicação execute outra etapa fora de ordem. Hooks do Claude Code pertencem aos eventos e permissões desse produto; não são um mecanismo genérico da Messages API. Em uma aplicação com client tools, o gate pertence ao código que recebe as respostas e executa os handlers.

5. Exercício integrado: papel → tools → turnos → gate

Scenario (EN). You are designing a research and document pipeline with a coordinator and three subagents: web search, document analysis, and synthesis. Available tools include search_web, load_document, extract_metadata, enrich_document, verify_fact (simple checks only), parse_pdf, parse_csv, and generic fetch_url. Complex investigations belong to search; enrichment requires a valid document_id from successful extraction.

Cenário. Você está desenhando um pipeline de pesquisa e documentos com um coordinator e três subagents: web search, análise de documentos e síntese. As tools disponíveis incluem search_web, load_document, extract_metadata, enrich_document, verify_fact (somente checagens simples), parse_pdf, parse_csv e a genérica fetch_url. Investigações complexas pertencem ao search; enrichment exige um document_id válido obtido por extração bem-sucedida.
  1. Role → tool matrix. Produce a matrix for search, document analysis, and synthesis with allowed tools, explicitly excluded tools, and a least-privilege justification. Keep enrichment gated and route complex fact-checking through the coordinator.
    Produza uma matriz para search, análise de documentos e síntese com tools permitidas, tools explicitamente excluídas e justificativa de least privilege. Mantenha enrichment sob gate e roteie checagens complexas pelo coordinator.
  2. tool_choice per turn. Choose and justify each setting: (A) synthesis may answer from supplied evidence or optionally call verify_fact; (B) an import must call either parse_pdf or parse_csv, never return conversational text; (C) a new document must request exactly extract_metadata first, with enrichment only after validation.
    Escolha e justifique cada configuração: (A) síntese pode responder com as evidências fornecidas ou, opcionalmente, chamar verify_fact; (B) uma importação deve chamar parse_pdf ou parse_csv, nunca devolver texto conversacional; (C) um documento novo deve solicitar exatamente extract_metadata primeiro, com enrichment somente após validação.
  3. Prerequisite gate. Write pseudocode for the complete client-tool loop. Include one success branch and separate failure branches for handler error and missing document_id. Show the tool_result, keep enrichment disabled on both failures, and define retry/recovery.
    Escreva pseudocódigo para o loop completo de client tool. Inclua um ramo de sucesso e ramos de falha separados para erro do handler e document_id ausente. Mostre o tool_result, mantenha enrichment desabilitado nas duas falhas e defina retry/recuperação.

Critérios de autocorreção: a matriz mínima esperada é search → search_web; document analysis → load_document, extract_metadata e enrich_document (esta última só após o gate); synthesis → verify_fact escopada, com investigação complexa via coordinator. A genérica fetch_url não deve ser distribuída sem necessidade e enforcement no handler. Nos turnos, A = "auto", B = "any" (as duas tools de parser são aceitáveis), C = forced extract_metadata + gate da aplicação. O pseudocódigo precisa validar sucesso e dados, não apenas a emissão do tool_use.

⚠️ Pegadinha do dia

Questões de misrouting quase sempre oferecem os mesmos três distratores: few-shot examples no system prompt (remendo caro quando a causa é a descrição mínima), routing layer por keywords (over-engineering que ignora a capacidade de linguagem do modelo) e fundir as tools numa genérica única (esforço grande demais para um primeiro passo). Quando o requisito é determinístico ("the model MUST call a tool"), o distrator clássico é a frase imperativa no prompt — tool_choice garante a emissão exigida, mas não a ordem executada nem o sucesso. Regra de bolso: descrição mínima ou sobreposta se conserta na descrição (primeiro passo); instrução por palavra-chave no system prompt se conserta reescrevendo-a por intenção; pedido genuinamente ambíguo, com descrições já boas, pede 2–4 few-shot com o raciocínio da escolha (TS 4.2, aula 09); emissão de tool_use se impõe com tool_choice; sequência real e pré-requisitos se impõem com gate na aplicação; restrição de load_document exige handler que valida e rejeita.
