Aula 06 — CLAUDE.md: hierarquia, @import e rules com glob

Domínio 3 · Claude Code Configuration & Workflows (20%) ~60 min
🎯 Objetivo do dia. Dominar a hierarquia de CLAUDE.md (user / project / directory), saber modularizar com @import e .claude/rules/, e escolher rules com glob no frontmatter quando uma convenção precisa seguir o tipo do arquivo e não o diretório. Ao final, distinguir contexto persistente, procedimento sob demanda, permissões, permission modes e hooks — incluindo qual garantia cada mecanismo realmente oferece.

1. A hierarquia de CLAUDE.md (Task Statement 3.1)

O Claude Code carrega instruções de três níveis, que se somam no contexto da sessão:

  • User-level — ~/.claude/CLAUDE.md. Suas preferências pessoais, válidas em todos os seus projetos, só para você. Ponto crítico da prova: este arquivo fica no seu home, fora do repositório — portanto não é compartilhado com o time via version control.
  • Project-level — CLAUDE.md na raiz do repo (ou .claude/CLAUDE.md). É commitado no VCS: padrões do projeto, convenções de teste, comandos de build — tudo que o time inteiro precisa receber igual.
  • Directory-level — CLAUDE.md em subdiretórios. Convenções específicas daquela parte da árvore (ex.: packages/billing/CLAUDE.md). Carrega quando o Claude trabalha em arquivos daquele diretório.
~/.claude/CLAUDE.md              # pessoal, NÃO vai pro git, só vale pra você
meu-repo/
├── CLAUDE.md                    # project-level: commitado, time inteiro recebe
├── .claude/
│   └── rules/                   # rules modulares (ver seções 3 e 4)
├── packages/
│   ├── billing/
│   │   └── CLAUDE.md            # directory-level: só ao mexer em billing/
│   └── api/
│       └── CLAUDE.md

O diagnóstico que a prova cobra

O Task Statement 3.1 cita explicitamente: "a new team member not receiving instructions because they're in user-level rather than project-level configuration". Tradução do cenário: você escreveu as convenções do time, funciona na sua máquina, mas o colega novo clona o repo e o Claude dele ignora tudo. Causa raiz: as instruções estão em ~/.claude/CLAUDE.md (seu home), que não viaja pelo git. Correção: mover para o project-level (CLAUDE.md na raiz ou .claude/CLAUDE.md), que é versionado.

/memory e /context: diagnosticar sem confundir

Quando o comportamento do Claude está inconsistente, comece pela configuração, não pela reescrita. /memory lista localizações de memórias e permite abri-las/criá-las no editor; ele não é o inventário do que a sessão carregou. Para verificar os CLAUDE.md e rules carregados no início, use /context e confira a seção Memory files.

Arquivos sob demanda pedem outro diagnóstico: reproduza o caso trabalhando com um arquivo que dá match no path. Um CLAUDE.md de subdiretório, por exemplo, não aparece na lista inicial do /context; ao carregar, seu caminho aparece numa linha Loaded no terminal. Para registrar o que carregou, quando e por quê — inclusive rules por path — use um hook InstructionsLoaded. Portanto, não espere que uma chamada a /context liste todos os arquivos que ainda podem entrar no contexto durante o trabalho.

2. Modularizando: @import e .claude/rules/ (Task Statement 3.1)

Um CLAUDE.md monolítico de 2.000 linhas é impossível de manter e pesa em toda sessão. O Exam Guide dá duas saídas de organização, complementares. Atenção: modularizar não corta contexto por si só — arquivos importados e rules sem paths continuam carregando em toda sessão; quem economiza tokens é o escopo por glob (seção 3, TS 3.3).

@import — referenciar arquivos externos

A sintaxe @caminho/do/arquivo dentro de um CLAUDE.md importa outro arquivo naquele ponto. Serve para manter o CLAUDE.md enxuto e importar só os standards relevantes para cada pacote — o guide dá o exemplo de cada package de um monorepo importar os standards do seu domínio:

# packages/payments/CLAUDE.md
# Convenções do pacote de pagamentos

@../../docs/standards/api-conventions.md
@../../docs/standards/testing.md

.claude/rules/ — arquivos por tópico

A alternativa estrutural: quebrar o CLAUDE.md gigante em arquivos focados dentro de .claude/rules/ — ex.: testing.md, api-conventions.md, deployment.md. Em vez de um documento único que mistura tudo, cada regra vive no seu próprio arquivo versionado. E, como veremos na próxima seção, esses arquivos podem ganhar escopo por glob.

3. Rules com glob: carregamento condicional por path (Task Statement 3.3)

Arquivos em .claude/rules/ aceitam YAML frontmatter com o campo paths, uma lista de glob patterns. Quando presente, a regra só entra no contexto quando o Claude trabalha com arquivos que dão match no glob — em vez de ficar carregada o tempo todo. Isso inclui Read, Write e Edit, além de leituras reconhecidas via Bash, como cat ou head em um único arquivo: não é somente ao editar.

# .claude/rules/testing.md
---
paths: ["**/*.test.tsx", "**/*.spec.tsx"]
---

- Use React Testing Library, nunca enzyme
- Todo teste de hook usa renderHook
- Fixtures ficam em __fixtures__ ao lado do teste
# .claude/rules/infra.md
---
paths: ["terraform/**/*"]
---

- Toda variável tem description e type
- Nada de recursos sem tags obrigatórias

Por que isso vence o CLAUDE.md de diretório

Dois ganhos, e os dois são o coração do Task Statement 3.3:

  1. Economia de contexto: a regra de testes só ocupa tokens quando você está de fato trabalhando com um *.test.tsx, inclusive na leitura. Regra sempre carregada = contexto irrelevante na maioria dos turnos.
  2. Convenção por TIPO de arquivo, não por lugar: o CLAUDE.md de subdiretório é directory-bound — só cobre aquela árvore. Mas arquivos de teste costumam ficar espalhados ao lado do código que testam (Button.test.tsx junto de Button.tsx). Para cobrir todos, você teria que replicar um CLAUDE.md em dezenas de pastas. O glob **/*.test.tsx resolve em um único arquivo, não importa o diretório.

Essa é exatamente a lógica da Questão 6 oficial do guide: áreas com convenções diferentes + arquivos de teste espalhados pelo codebase → a resposta é .claude/rules/ com frontmatter de globs. Seleção e carregamento pelo path podem ser determinísticos; a aderência do modelo à instrução continua probabilística. Quando a convenção precisa de enforcement, ainda é necessário um mecanismo programático.

4. Mapa de decisão rápido

Orientação × garantia. CLAUDE.md, @import e rules fornecem contexto: o modelo lê e tende a seguir, mas sua aderência é probabilística — mesmo quando a seleção pelo path é determinística. Uma Skill empacota um procedimento reutilizável sob demanda: pode ser invocada explicitamente ou carregada automaticamente quando o Claude a considera relevante para a tarefa. Seleção automática não a torna orientação always-on nem substitui o contexto persistente do CLAUDE.md.

Para controle de execução, o Claude Code oferece mecanismos distintos. Regras de permissão e hooks ficam nos arquivos de settings (usuário ~/.claude/settings.json, projeto .claude/settings.json versionado, local .claude/settings.local.json):

  • Regras de permissão (settings.permissions com allow / ask / deny): permitem, pedem aprovação ou bloqueiam alvos como tools, comandos e paths. São avaliadas na ordem deny → ask → allow — um deny vence qualquer allow. Entre arquivos, a precedência é managed > linha de comando > local > projeto > usuário, e as listas de regras se somam entre eles em vez de uma substituir a outra.
  • Hooks de comando: executam código em eventos — por exemplo, validar ou bloquear uma ação antes de ela ocorrer, ou formatar e verificar estilo depois de uma edição. Também podem vir de plugins e do frontmatter de skills e subagents.
  • Permission modes: controlam o nível geral de autonomia e aprovação da sessão. Não são uma regra allow/ask/deny para um alvo específico nem uma verificação executada em um evento.
// .claude/settings.json  (commitado: vale para o time todo)
{
  "permissions": {
    "deny": ["Read(**/.env)", "Read(./secrets/**)", "Bash(terraform apply:*)"]
  }
}

Regra de bolso: o que o Claude deve saber ou considerar vai no CLAUDE.md/rules; um procedimento reutilizável sob demanda vai numa Skill; permissão por alvo vai em settings.permissions; ação ou verificação em evento vai num hook de comando; autonomia geral vai no permission mode. Convenção de estilo ou de nomes pode ser orientação em CLAUDE.md/rules, mas, se houver um critério executável, um hook de comando também pode validar, formatar ou bloquear em um evento. O deny tem alcance: cobre as tools nativas e os comandos que o Claude Code reconhece (cat, head, redirecionamentos), não um script Python ou Node que abre o arquivo por conta própria — bloqueio no nível do sistema operacional pede o sandbox.

Detalhe de sintaxe: Read(./.env) casa só com o .env do diretório atual; para todos os .env do repositório, use Read(**/.env).

⚠️ Pegadinha do dia

Questões de configuração adoram o distrator "consolide tudo no CLAUDE.md raiz e deixe o Claude inferir qual seção se aplica". A seleção/carregamento de uma rule por path pode ser determinística, mas a aderência à instrução continua probabilística; enforcement exige outro mecanismo. Também aparece muito o distrator "instruções no ~/.claude/CLAUDE.md" para regras de time — arquivo de usuário não viaja pelo git.

Não trate Skill como sinônimo de invocação manual: ela também pode ser carregada por relevância, mas continua sob demanda, não always-on. Estilo e nomes podem ser orientação em CLAUDE.md/rules ou verificação/formatação/ bloqueio em hook de comando quando houver critério executável. No diagnóstico, /context verifica o início da sessão; /memory localiza e edita memórias; arquivos sob demanda exigem reproduzir o acesso correspondente.
