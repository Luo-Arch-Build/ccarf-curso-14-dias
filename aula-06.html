Aula 06 — CLAUDE.md: hierarquia, @import e rules com glob

Domínio 3 · Claude Code Configuration & Workflows (20%) ~60 min
🎯 Objetivo do dia. Dominar a hierarquia de CLAUDE.md (user / project / directory), saber modularizar com @import e .claude/rules/, e escolher rules com glob no frontmatter quando uma convenção precisa seguir o tipo do arquivo e não o diretório — o caso clássico dos arquivos de teste espalhados pelo codebase.

1. A hierarquia de CLAUDE.md (Task Statement 3.1)

O Claude Code carrega instruções de três níveis, que se somam no contexto da sessão:

  • User-level — ~/.claude/CLAUDE.md. Suas preferências pessoais, válidas em todos os seus projetos, só para você. Ponto crítico da prova: este arquivo fica no seu home, fora do repositório — portanto não é compartilhado com o time via version control.
  • Project-level — CLAUDE.md na raiz do repo (ou .claude/CLAUDE.md). É commitado no VCS: padrões do projeto, convenções de teste, comandos de build — tudo que o time inteiro precisa receber igual.
  • Directory-level — CLAUDE.md em subdiretórios. Convenções específicas daquela parte da árvore (ex.: packages/billing/CLAUDE.md). Carrega quando o Claude trabalha em arquivos daquele diretório.
~/.claude/CLAUDE.md              # pessoal, NÃO vai pro git, só vale pra você
meu-repo/
├── CLAUDE.md                    # project-level: commitado, time inteiro recebe
├── .claude/
│   └── rules/                   # rules modulares (ver seções 3 e 4)
├── packages/
│   ├── billing/
│   │   └── CLAUDE.md            # directory-level: só ao mexer em billing/
│   └── api/
│       └── CLAUDE.md

O diagnóstico que a prova cobra

O Task Statement 3.1 cita explicitamente: "a new team member not receiving instructions because they're in user-level rather than project-level configuration". Tradução do cenário: você escreveu as convenções do time, funciona na sua máquina, mas o colega novo clona o repo e o Claude dele ignora tudo. Causa raiz: as instruções estão em ~/.claude/CLAUDE.md (seu home), que não viaja pelo git. Correção: mover para o project-level (CLAUDE.md na raiz ou .claude/CLAUDE.md), que é versionado.

/memory: o diagnóstico de primeira linha

Quando o comportamento do Claude está inconsistente entre sessões ou entre máquinas, o primeiro passo não é reescrever nada — é inspecionar o que está carregado. O comando /memory mostra quais arquivos de memória (CLAUDE.md de cada nível, rules) estão ativos na sessão. É o equivalente a "verificar as variáveis de ambiente" antes de culpar o código.

2. Modularizando: @import e .claude/rules/ (Task Statement 3.1)

Um CLAUDE.md monolítico de 2.000 linhas é impossível de manter e pesa em toda sessão. O Exam Guide dá duas saídas de organização, complementares. Atenção: modularizar não corta contexto por si só — arquivos importados e rules sem paths continuam carregando em toda sessão; quem economiza tokens é o escopo por glob (seção 3, TS 3.3).

@import — referenciar arquivos externos

A sintaxe @caminho/do/arquivo dentro de um CLAUDE.md importa outro arquivo naquele ponto. Serve para manter o CLAUDE.md enxuto e importar só os standards relevantes para cada pacote — o guide dá o exemplo de cada package de um monorepo importar os standards do seu domínio:

# packages/payments/CLAUDE.md
# Convenções do pacote de pagamentos

@../../docs/standards/api-conventions.md
@../../docs/standards/testing.md

.claude/rules/ — arquivos por tópico

A alternativa estrutural: quebrar o CLAUDE.md gigante em arquivos focados dentro de .claude/rules/ — ex.: testing.md, api-conventions.md, deployment.md. Em vez de um documento único que mistura tudo, cada regra vive no seu próprio arquivo versionado. E, como veremos na próxima seção, esses arquivos podem ganhar escopo por glob.

3. Rules com glob: carregamento condicional por path (Task Statement 3.3)

Arquivos em .claude/rules/ aceitam YAML frontmatter com o campo paths, uma lista de glob patterns. Quando presente, a regra só entra no contexto quando o Claude está editando arquivos que dão match no glob — em vez de ficar carregada o tempo todo.

# .claude/rules/testing.md
---
paths: ["**/*.test.tsx", "**/*.spec.tsx"]
---

- Use React Testing Library, nunca enzyme
- Todo teste de hook usa renderHook
- Fixtures ficam em __fixtures__ ao lado do teste
# .claude/rules/infra.md
---
paths: ["terraform/**/*"]
---

- Toda variável tem description e type
- Nada de recursos sem tags obrigatórias

Por que isso vence o CLAUDE.md de diretório

Dois ganhos, e os dois são o coração do Task Statement 3.3:

  1. Economia de contexto: a regra de testes só ocupa tokens quando você está de fato editando um *.test.tsx. Regra sempre carregada = contexto irrelevante na maioria dos turnos.
  2. Convenção por TIPO de arquivo, não por lugar: o CLAUDE.md de subdiretório é directory-bound — só cobre aquela árvore. Mas arquivos de teste costumam ficar espalhados ao lado do código que testam (Button.test.tsx junto de Button.tsx). Para cobrir todos, você teria que replicar um CLAUDE.md em dezenas de pastas. O glob **/*.test.tsx resolve em um único arquivo, não importa o diretório.

Essa é exatamente a lógica da Questão 6 oficial do guide: áreas com convenções diferentes + arquivos de teste espalhados pelo codebase → a resposta é .claude/rules/ com frontmatter de globs, porque é o único mecanismo que aplica a convenção deterministamente pelo path do arquivo.

⚠️ Pegadinha do dia

Questões de configuração adoram o distrator "consolide tudo no CLAUDE.md raiz e deixe o Claude inferir qual seção se aplica". Inferência não é garantia: é o remendo probabilístico onde se pede aplicação determinística por path. Também aparece muito o distrator "instruções no ~/.claude/CLAUDE.md" para regras de time — arquivo de usuário não viaja pelo git. Regra de bolso: convenção de time vai no que é versionado; convenção por tipo de arquivo vai em .claude/rules/ com glob; e antes de reescrever configuração, rode /memory para ver o que está carregado.
