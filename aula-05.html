É a aula mais "engenharia de produção" do domínio.

1. Erros estruturados em MCP tools (Task Statement 2.2)

1.1 O flag isError

No MCP, uma tool que falhou não lança exceção para o modelo — ela devolve um resultado normal com o flag isError: true. É assim que o servidor comunica a falha de volta ao agente, que lê o conteúdo do erro e decide o que fazer em seguida. Ou seja: o erro é um dado que entra no raciocínio do modelo, não um crash do loop.

1.2 As quatro categorias de erro

A prova cobra a distinção porque cada categoria pede uma reação diferente do agente:

  • transient (transitório): timeout, serviço indisponível, rate limit → vale tentar de novo, talvez com backoff ou query modificada
  • validation (validação): input inválido, formato errado → não adianta repetir o mesmo input; o agente precisa corrigir os parâmetros
  • business (negócio): violação de regra de política (ex.: reembolso acima do teto) → nunca é retryable; o agente deve explicar ao usuário e/ou escalar
  • permission (permissão): credencial inválida, acesso negado → retry imediato é inútil; precisa de intervenção (novo token, outro escopo)

1.3 Por que "Operation failed" é um anti-padrão

Se toda falha devolve a mesma mensagem genérica, o agente não consegue tomar a decisão de recuperação correta: ele não sabe se deve tentar de novo, corrigir o input, escalar ou desistir. O resultado típico em produção: retry de erro de validação (queimando tokens e latência num caso sem chance) e desistência de erro transitório (que se resolveria com uma nova tentativa). A correção é devolver metadata estruturada junto com o erro:

{
  "isError": true,
  "content": [{
    "type": "text",
    "text": "Refund declined: amount $780 exceeds the $500 policy limit. A human agent must approve refunds above this threshold."
  }],
  "errorCategory": "business",
  "isRetryable": false
}

O trio que a prova espera: errorCategory (o guide lista transient/validation/permission), isRetryable (boolean) e uma descrição human-readable. Para violações de regra de negócio, inclua retriable: false (ou isRetryable: false) e uma explicação amigável ao cliente, para o agente comunicar a decisão corretamente em vez de tentar de novo.

1.4 Retryable vs non-retryable

A metadata estruturada evita tentativas de retry desperdiçadas: sem ela, a única estratégia do agente é chutar. Com isRetryable: false ele encerra na hora e explica; com isRetryable: true ele tenta de novo com critério. Um erro de validação é non-retryable com o mesmo input — mas o agente pode corrigir o parâmetro e chamar de novo, e a descrição do erro é o que permite essa correção.

1.5 Falha de acesso ≠ resultado vazio válido

Distinção fina que a prova adora: uma query que executou com sucesso e não achou nada (empty result válido) é um sucesso — o dado simplesmente não existe. Uma falha de acesso (timeout, 503) é um erro — o dado pode existir, mas não foi consultado. Se o servidor devolve resultado vazio nos dois casos (ou pior: devolve vazio marcado como sucesso num timeout), o agente conclui "não há pedidos para esse cliente" quando na verdade o banco estava fora do ar. Empty result não carrega isError; falha de acesso carrega isError: true + categoria + retryability.

1.6 Recuperação local no subagent, propagação enxuta

Num sistema multi-agent, a regra é: o subagent resolve localmente o que consegue (erros transitórios: retry com backoff, query alternativa) e só propaga ao coordinator o que não conseguiu resolver — e quando propaga, manda contexto estruturado: tipo da falha, o que foi tentado, resultados parciais obtidos e alternativas possíveis. Três anti-padrões — os dois primeiros, simétricos:

  • ❌ Suprimir o erro (devolver vazio como sucesso) → o coordinator nem sabe que houve falha e não pode recuperar
  • ❌ Derrubar o workflow inteiro numa única falha → perde todo o trabalho parcial que poderia sustentar uma resposta
  • ❌ Propagar status genérico ("search unavailable") → esconde do coordinator a informação que ele precisaria para decidir (retry? fonte alternativa? seguir com parcial?)

2. MCP servers no Claude Code (Task Statement 2.4)

2.1 Escopo: project-level vs user-level

Existem dois lugares para configurar MCP servers, e escolher o errado é o sintoma clássico das questões ("o dev novo clonou o repo e o server não aparece"):

  • .mcp.json na raiz do projeto (project-level): commitado no VCS, compartilhado com o time inteiro automaticamente no clone/pull. Use para tooling padrão do projeto (GitHub, Jira, banco de staging).
  • ~/.claude.json (user-level): fica na home do desenvolvedor, não vai para o VCS. Use para servers pessoais ou experimentais que ninguém mais precisa ter.

2.2 Expansão de variável de ambiente (segredos fora do VCS)

O .mcp.json vai para o git — então tokens nunca podem estar hardcoded nele. A solução é a expansão de variável de ambiente: o arquivo referencia ${GITHUB_TOKEN} e cada desenvolvedor define a variável no próprio ambiente. O config é compartilhado; o segredo, não.

// .mcp.json  (commitado no repo — sem segredos!)
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}

À esquerda, a variável que o server lê; à direita, a variável do ambiente de cada dev, expandida pelo Claude Code ao subir o server.

2.3 Descoberta de tools no connect

Quando o Claude Code conecta nos MCP servers configurados, as tools de todos os servers são descobertas no momento da conexão e ficam disponíveis simultaneamente para o agente. Não existe "ativar um server por vez": o modelo vê o catálogo completo e escolhe — o que reforça a importância de descrições boas (aula 04) para ele não confundir tools de servers diferentes.

🧭 Prova × produto atual (documentação do Claude Code conferida em 20/10/2026)
  • Com o tool search, ligado por padrão, as definições das MCP tools são carregadas sob demanda: todas continuam utilizáveis na sessão, sem limite por server, mas não entram todas no contexto de uma vez.
  • MCP resources aparecem nas menções com @ (ex.: @server:protocol://resource/path), ao lado dos arquivos.
Na prova vale o texto do guia: tools de todos os servers descobertas na conexão e disponíveis simultaneamente.

2.4 MCP resources: catálogo de conteúdo

Tools são ações; resources são conteúdo. Expor um catálogo como MCP resource — sumários de issues, hierarquia da documentação, schema do banco — dá ao agente visibilidade do que existe sem que ele precise fazer dezenas de tool calls exploratórias só para descobrir os dados. Sintoma típico de questão: "o agente gasta muitas chamadas explorando a estrutura antes de começar o trabalho real" → exponha o catálogo como resource. Regra de bolso: se o agente chama tools só para descobrir o que existe, falta catálogo — exponha-o como resource. Cache deixa cada descoberta mais rápida, mas não elimina as chamadas.

2.5 Servers da comunidade primeiro

Para integrações padrão (Jira, GitHub, Slack, Postgres), prefira MCP servers prontos da comunidade em vez de escrever um custom do zero. Reserve o esforço de implementação custom para workflows específicos do seu time que nenhum server existente cobre. Over-engineering clássico de distrator: "construir um MCP server próprio para integrar com o Jira". Regra de bolso: integração que todo mundo usa → server da comunidade; fluxo que só o seu time tem → server custom. E lembre que todos convivem: as tools de todos os servers ficam disponíveis juntas.

2.6 Descrições boas vencem o Grep

Se a descrição de um MCP tool é fraca, o agente tende a preferir as tools nativas que ele já conhece bem — ex.: usar Grep em arquivos exportados em vez de chamar um MCP tool de busca semântica muito mais capaz. A correção é detalhar a descrição do MCP tool (capacidades, formato de saída, quando preferi-lo às alternativas), não restringir o Grep nem adicionar regras no prompt. Regra de bolso: quando o agente ignora uma MCP tool melhor, a culpa é da descrição dela — conserte a descrição antes de tirar tools do agente ou escrever regra no prompt.

3. Tools nativas: Read, Write, Edit, Grep, Glob (Task Statement 2.5)

3.1 Tabela de seleção

ToolPergunta que ela respondeExemplo
Greponde está este conteúdo?todos os callers de process_refund, onde a mensagem de erro X é lançada, imports de um módulo
Globonde estão os arquivos com este nome/padrão?**/*.test.tsx, src/**/index.ts
Reado que há neste arquivo inteiro?carregar um arquivo para entender ou reescrever
Writegravar conteúdo completo em arquivocriar arquivo novo ou sobrescrever após Read
Editmodificação cirúrgica via texto âncora únicotrocar o corpo de uma função cujo trecho aparece uma só vez

Regra de bolso: Grep busca dentro dos arquivos; Glob busca os arquivos. Questões trocam os dois de propósito ("qual tool para achar todos os arquivos *.test.tsx?" → Glob, não Grep).

3.2 O fallback Edit → Read + Write

O Edit só funciona quando o texto âncora é único no arquivo. Se o trecho aparece várias vezes (ex.: return null; num arquivo grande), o Edit falha — e a resposta certa não é insistir no mesmo Edit nem apelar para sed via Bash. O padrão confiável é o fallback: Read do arquivo inteiro → modificar → Write de volta. Mais tokens, mas confiável.

3.3 Exploração incremental de codebase

O anti-padrão é ler tudo de uma vez ("leia os 200 arquivos do repo e me explique"). A exploração eficiente é incremental:

  1. Grep para achar entry points (ex.: onde a rota é registrada, onde a função pública é exportada)
  2. Read nos arquivos encontrados, seguindo os imports para rastrear o fluxo
  3. Repita: cada Read revela os próximos arquivos relevantes

Para rastrear o uso de uma função através de módulos wrapper: primeiro liste todos os nomes exportados do wrapper, depois faça Grep de cada nome no codebase — procurar só o nome original da função perde os call sites que importam via re-export. Regra de bolso: ponto de entrada → Read → imports, nunca "ler tudo antes"; e, para achar todos os chamadores, levante primeiro todos os nomes exportados.

⚠️ Pegadinha do dia

Questões de erro quase sempre oferecem dois distratores gêmeos: "adicione retry automático para qualquer falha" e "devolva resultado vazio marcado como sucesso quando a consulta falhou". Os dois nascem da mesma confusão: sem categoria de erro, toda falha vira igual. Retry cego queima tokens em erros de validação/negócio que nunca vão se resolver; vazio-como-sucesso numa falha de acesso esconde o problema do coordinator. O inverso também é erro: tratar como falha uma consulta bem-sucedida sem matches vira alarme falso. Regra de bolso: o agente só se recupera bem se o erro disser a categoria e a retryability — "Operation failed" não diz nada; consulta bem-sucedida sem matches não é erro, é resposta; falha de acesso nunca vira vazio.

Gabarito: A e D. O guide descreve a exploração incremental: Grep acha os pontos de entrada, Read carrega esses arquivos e os imports levam ao resto do fluxo (A). Para achar todos os chamadores, primeiro levante todos os nomes exportados — inclusive reexportações em módulos wrapper — e busque cada um (D); procurar só o nome original perde quem importa pelo apelido. B e C são variações de "ler tudo antes": gastam o contexto com arquivos irrelevantes e atrasam a resposta.
