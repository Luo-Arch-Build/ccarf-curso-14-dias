Aula 01 — A prova e o loop agêntico

Domínio 1 · Agentic Architecture & Orchestration (27%) ~60 min
🎯 Objetivo do dia. Entender o formato exato da prova CCAR-F e dominar o agentic loop — o ciclo de vida de um agente que decide sozinho qual tool chamar, guiado pelo stop_reason. É a fundação do domínio mais pesado do exame.

1. A prova em 2 minutos

A Claude Certified Architect – Foundations (código CCAR-F) valida que você toma boas decisões de tradeoff ao implementar soluções reais com Claude. Os números:

  • 60 questões de múltipla escolha e múltipla resposta (a questão diz quantas marcar)
  • 120 minutos → 2 min por questão
  • 4 cenários por prova, sorteados de um banco público de 6 (suporte ao cliente, geração de código, pesquisa multi-agent, produtividade dev, CI/CD, extração de dados)
  • Nota de corte 720 numa escala de 100–1000
  • Proctored pela Pearson VUE, em inglês ou japonês (não há português — para nós, inglês), mesa limpa (sem anotações, sem segundo monitor, sem tradutor do navegador)

O padrão das questões: um cenário de produção — quase sempre um sintoma, às vezes um requisito de configuração ou desenho — + alternativas plausíveis (4 na múltipla escolha; na múltipla resposta, a questão diz quantas marcar). A resposta certa quase sempre é a que ataca a causa raiz com a solução proporcional — nem remendo cosmético, nem over-engineering. Guarde isso: ele reaparece em todas as aulas.

Sobre a múltipla resposta: o guia prevê questões do tipo "select TWO", e o curso mantém algumas para treino. Mas um candidato que já fez a prova relatou ter visto só questões de resposta única. Um relato não prova nada: treine os dois formatos, mas não conte com a múltipla resposta aparecendo, nem estranhe se ela não vier.

2. O agentic loop (Task Statement 1.1)

Um agente não é "uma chamada à API". É um loop: o modelo raciocina, pede uma tool, recebe o resultado, raciocina de novo — até decidir que terminou. O ciclo de vida:

  1. Você envia a conversa + a lista de tools disponíveis
  2. Claude responde com um stop_reason:
    • "tool_use" → ele quer executar uma tool. Continue o loop.
    • "end_turn" → ele terminou e deu a resposta final. Encerre o loop.
  3. Se foi tool_use: execute a tool, adicione o resultado ao histórico da conversa (como uma mensagem tool_result) e chame a API de novo
  4. Repita até end_turn
while True:
    response = client.messages.create(model=..., messages=messages, tools=tools)
    if response.stop_reason == "end_turn":
        break                      # resposta final ao usuário
    if response.stop_reason != "tool_use":
        handle_other(response)     # ex.: "max_tokens" = saída truncada
        break
    # stop_reason == "tool_use": executar e devolver resultados
    results = [execute(block) for block in response.content if block.type == "tool_use"]
    messages.append({"role": "assistant", "content": response.content})
    messages.append({"role": "user", "content": results})   # tool_result blocks

Os outros valores de stop_reason

O guia fala de "tool_use" e "end_turn", mas a API documenta mais cinco. O loop precisa saber o que fazer com cada um, porque nenhum deles é "terminei com sucesso":

stop_reasonO que aconteceuO que o loop faz
tool_useo modelo pediu uma ou mais toolsexecuta todas e devolve os resultados; continua
end_turnresposta finalencerra e entrega
max_tokensa saída bateu no limite e veio cortadatrata como incompleta (aula 10: dividir a tarefa)
stop_sequenceapareceu uma sequência de parada que você configurousegue a regra que você definiu para ela
pause_turno loop de server tools do lado da API (ex.: busca web) atingiu o limite de iteraçõesdevolve a resposta como está, num novo request, para o modelo continuar
refusalo modelo recusou (HTTP 200, não é erro; o motivo vem em stop_details)não repete o mesmo request em loop; lê stop_details e trata como recusa ou tenta outro modelo
model_context_window_exceededa geração parou porque a janela de contexto do modelo encheutrata como saída truncada, igual a max_tokens: não usa o resultado como se estivesse completo

Regra de bolso: "end_turn" encerra com resposta pronta e só "tool_use" pede execução de tool; os demais pedem tratamento próprio, nunca "sucesso" nem um retry cego. O caso oposto: um "stop_sequence" que você mesmo definiu como delimitador de fim também entrega resposta completa.

Várias tool calls numa única resposta

Uma mesma resposta do modelo pode trazer vários blocos tool_use: por exemplo, lookup_order para dois pedidos diferentes. É assim que o loop paraleliza subtarefas independentes e economiza idas e voltas à API. O contrato:

  • Execute todos os blocos (em paralelo, se forem independentes).
  • Devolva todos os tool_result numa única mensagem user, cada um com o tool_use_id do bloco a que responde. O loop acima já faz isso: a lista results vai inteira numa mensagem só.
  • Tool que falhou continua tendo resultado: tool_result com "is_error": true e a mensagem do erro. Omitir o resultado quebra o histórico: um tool_use sem tool_result correspondente faz a API rejeitar o request seguinte com erro 400.
{"role": "user", "content": [
  {"type": "tool_result", "tool_use_id": "toolu_01A", "content": "{\"order\": 4471, \"status\": \"shipped\"}"},
  {"type": "tool_result", "tool_use_id": "toolu_01B", "content": "order not found", "is_error": true}
]}

Erro comum, citado na documentação: mandar cada tool_result numa mensagem user separada. A API aceita, mas o histórico passa a mostrar uma chamada por vez, e isso "ensina" o modelo a parar de fazer chamadas paralelas. Para limitar de propósito, use disable_parallel_tool_use: true no tool_choice: com "auto", no máximo uma tool por resposta; com "any" ou tool forçada, exatamente uma.

Regra de bolso: subtarefas independentes → deixe o modelo pedir várias tools na mesma resposta e devolva tudo junto; quando uma depende do resultado da outra, ela vem naturalmente no turno seguinte, e serializar é o certo.

O ponto conceitual que a prova cobra

A decisão de qual tool chamar e quando parar é model-driven: o próprio Claude raciocina sobre o contexto e escolhe o próximo passo. Isso é o oposto de uma decision tree pré-configurada (fluxo fixo de tools). A arquitetura agêntica delega o roteamento ao modelo — seu trabalho como arquiteto é dar a ele boas tools, bom contexto e boas barreiras.

Anti-padrões (a prova ADORA cobrar isso)

  • ❌ Parsear linguagem natural pra decidir quando parar ("se a resposta contém 'pronto', encerre") — frágil; use o stop_reason, que é o sinal estrutural
  • ❌ Cap arbitrário de iterações como mecanismo principal de parada ("rode no máximo 10 vezes") — cap é cinto de segurança, não estratégia de término
  • ❌ Checar se o assistant gerou texto como indicador de conclusão — o modelo pode escrever texto intermediário e pedir tool no mesmo turno; quem manda é o stop_reason
  • ❌ Não devolver o tool_result ao histórico — sem isso o modelo não sabe o que aconteceu e não consegue raciocinar sobre o próximo passo

⚠️ Pegadinha do dia

Questões do tipo "o agente às vezes continua rodando depois de responder / para cedo". Os distratores oferecem heurísticas de texto ("verifique se a resposta contém X") ou caps numéricos. A resposta certa quase sempre envolve usar o stop_reason como sinal estrutural de controle do loop. Se o sintoma é "entra em loop chamando a mesma tool", o stop_reason continua "tool_use" e não resolve sozinho: confira primeiro se o resultado da tool está chegando ao histórico com conteúdo útil — sem ele o modelo não vê o que já buscou e repete o pedido. O cap é só rede de segurança. Regra de bolso: controle de fluxo do agente é responsabilidade do seu código, guiado pelo stop_reason — nunca inferido do texto que o modelo escreveu.

Questão 1 · múltipla escolha Customer Support Resolution Agent
Your support agent occasionally ends the conversation right after its first response. In every such case, the logged API response contains a short text block (“Let me check that order for you.”) followed by a tool_use block, and the customer receives only that text. What is the root cause?
Seu agente de suporte às vezes encerra a conversa logo após a primeira resposta. Em todos esses casos, a resposta da API registrada no log contém um bloco de texto curto (“Vou verificar esse pedido para você.”) seguido de um bloco tool_use, e o cliente recebe só esse texto. Qual é a causa raiz?
Gabarito: B. O modelo pode perfeitamente emitir texto e um bloco tool_use no mesmo turno — texto não significa "terminei". O sinal estrutural é o stop_reason: continue em "tool_use", encerre em "end_turn". A afirma uma limitação que não existe: texto e tool no mesmo turno é normal. C inventa um efeito das descrições — o enunciado diz que a tool foi pedida. D não explica nada: o padrão do log (texto + tool_use, e o cliente só recebe o texto) aponta para o loop tratando texto como fim, não para falta de histórico.Domínio 1 · TS 1.1 — Loop agêntico
Questão 2 · múltipla escolha Customer Support Resolution Agent
A teammate proposes simplifying the support agent by replacing the agentic loop with a hard-coded pipeline that, in every conversation, calls get_customer, then lookup_order, then process_refund. Why is this architecturally weaker than a model-driven agentic loop?
Um colega propõe simplificar o agente de suporte trocando o loop agêntico por um pipeline fixo que, em toda conversa, chama get_customer, depois lookup_order, depois process_refund. Por que isso é arquiteturalmente mais fraco que um loop agêntico model-driven?
Gabarito: A. O valor do agente é a decisão model-driven: cada pedido real é diferente (pergunta simples não precisa de refund; uma disputa de cobrança pode nem envolver pedido), e uma sequência fixa vira uma decision tree frágil. B é verdade parcial ("sempre" é exagero) e não é o argumento arquitetural central. C descreve uma limitação de API que não existe. D é falso duas vezes: boas descrições continuam sendo o principal mecanismo de seleção, e o modelo não "aprende" entre turnos — ele raciocina sobre o histórico que você envia. Não confunda com o prerequisite gate do TS 1.4 (aula 03): bloquear process_refund até get_customer devolver um ID verificado é uma barreira determinística de ordem, e o modelo continua decidindo o resto. Barreira programática sim, roteiro fixo de tools não.Domínio 1 · TS 1.1 — Loop agêntico
Questão 3 · múltipla escolha Multi-Agent Research System
Your research agent sometimes loops forever, calling the same search tool repeatedly. A colleague suggests ending the loop when the assistant writes "I have enough information." What is the best critique of this approach?
Seu agente de pesquisa às vezes entra em loop infinito, chamando a mesma tool de busca repetidamente. Um colega sugere encerrar o loop quando o assistant escrever "I have enough information." Qual é a melhor crítica a essa abordagem?
Gabarito: C. Linguagem natural é ambígua e não garantida — o modelo pode escrever a frase e ainda pedir outra tool, ou nunca escrevê-la. O término correto vem do stop_reason ("end_turn"). A só troca uma frase por várias: continua parseando texto. B põe o cap de iterações como mecanismo principal de parada — anti-padrão; o cap existe só como proteção contra loop infinito. D encerra antes de o modelo raciocinar sobre o resultado, quebrando o próprio loop. Note que o stop_reason não cura o loop do enunciado — ele continua "tool_use": a causa das buscas repetidas ainda precisa ser investigada (por exemplo, tool_result não devolvido ao histórico), e o cap segura o runaway enquanto isso.Domínio 1 · TS 1.1 — Loop agêntico

Questão 6 · múltipla escolha Multi-Agent Research System
Early in development, your research agent often requested web_search for three subtopics in one response. Since then the team changed three things: each tool_result is now appended as its own user message as soon as it finishes, turns older than 20 messages are trimmed, and the web_search description was shortened. Over later turns the agent starts requesting one search per turn, and total latency triples. Which change most likely caused it?
No começo do desenvolvimento, seu agente de pesquisa costumava pedir web_search para três subtópicos numa só resposta. Desde então o time mudou três coisas: cada tool_result passou a ser anexado como uma mensagem user própria assim que termina, turnos com mais de 20 mensagens de idade são cortados, e a descrição da web_search foi encurtada. Nos turnos seguintes o agente passa a pedir uma busca por turno, e a latência total triplica. Qual mudança é a causa mais provável?
Gabarito: C. Todos os tool_result de uma resposta vão numa única mensagem user, cada um com seu tool_use_id. Separados, o histórico mostra uma chamada por vez, e o modelo passa a imitar esse padrão; a documentação da API cita esse erro de formatação como a causa mais comum de o modelo parar de paralelizar. A mexe na seleção da tool, não no formato das chamadas: uma descrição mais curta pode piorar a escolha, mas não ensina a pedir uma busca por turno. B ataca o sintoma errado: cortar turnos antigos não muda o padrão que os turnos recentes mostram, e são eles, com um resultado por mensagem, que o modelo imita. D inverte o default: o paralelismo vem ligado, e o agente já paralelizava no começo; disable_parallel_tool_use serve para desligar.Domínio 1 · TS 1.1 — Loop agêntico
