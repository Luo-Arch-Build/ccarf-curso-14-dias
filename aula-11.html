Aula 11 — Message Batches API e review multi-pass

Domínio 4 · Prompt Engineering & Structured Output (20%) ~60 min
🎯 Objetivo do dia. Dominar dois Task Statements do Domínio 4: 4.5 (quando usar a Message Batches API — 50% mais barata, janela de até 24h, sem SLA de latência — e como operar batches: custom_id, resubmissão de falhas, amostra antes do volume) e 4.6 (arquiteturas de review multi-instância e multi-pass: por que self-review é fraco, como dividir reviews grandes em passes focados por arquivo + passe de integração cross-file, e quando separar passes por tipo de problema — segurança, lógica de negócio, design de API).

1. Message Batches API (Task Statement 4.5)

A Message Batches API processa conjuntos de requests de forma assíncrona. Os três números que definem TODAS as questões desse tema:

  • 50% de economia de custo em relação à API síncrona
  • Janela de processamento de até 24 horas (pode ser bem mais rápido, mas não é garantido)
  • Sem SLA de latência — não existe promessa de "termina em X minutos"

A regra de ouro: latência do workflow decide a API

A decisão nunca é "batch é mais barato, então migra tudo". É: o workflow é bloqueante ou tolerante a latência?

  • ✅ Apropriado (não-bloqueante): relatórios overnight de technical debt, auditorias semanais de código, geração noturna de testes, enriquecimento em massa de dados — qualquer coisa cujo resultado só é consumido horas depois
  • ❌ Inapropriado (bloqueante): pre-merge checks que travam o merge, respostas a usuário em tempo real, qualquer fluxo onde um humano (ou um pipeline) espera parado pelo resultado. Um check que pode levar até 24h destrói o fluxo de desenvolvimento

Repare nos distratores clássicos: "migre tudo e faça polling de status" (polling não cria SLA), "adicione um timeout com fallback pra API real-time" (complexidade desnecessária quando a solução simples é casar cada API com seu caso de uso).

Limitação estrutural: sem tool calling multi-turn dentro do batch

Um request de batch não suporta tool calling multi-turn: a API não executa tools no meio do request e devolve os resultados para o modelo continuar. Se seu workload precisa que o modelo chame tools e raciocine sobre os resultados (loop agêntico), isso tem que ser orquestrado por VOCÊ, fora do batch — ou o workload não é candidato a batch.

custom_id: a cola entre request e response

Os resultados de um batch podem vir fora de ordem. Cada request leva um custom_id definido por você, e cada resultado traz o mesmo custom_id de volta — é assim que você correlaciona request ↔ response e identifica exatamente quais itens falharam.

POST /v1/messages/batches
{
  "requests": [
    {
      "custom_id": "debt-report-src-billing-invoice-py",
      "params": {
        "model": "claude-...",
        "max_tokens": 2048,
        "messages": [{"role": "user", "content": "Analyze this file for technical debt: ..."}]
      }
    },
    ...
  ]
}

Operando batches: frequência, falhas e amostra

  • Frequência de submissão vs SLA: se o batch pode levar até 24h e você tem um SLA de 30h para entregar resultados, não dá pra submeter uma vez por dia — você precisa de janelas de folga (ex.: submeter a cada 4h), porque o pior caso é o documento que chega logo depois de uma submissão: ele espera o intervalo inteiro até a próxima e ainda pode levar 24h de processamento. Conta: intervalo entre submissões + 24h + folga ≤ SLA. Com SLA de 30h, o teto teórico é 6h, sem folga nenhuma; o exemplo do guia usa janelas de 4h (4 + 24 = 28h, com 2h de margem). Se a questão repetir os números do guia, a resposta é 4h.
  • Falhas: não resubmeta o batch inteiro. Filtre os resultados com erro pelo custom_id, corrija a causa (ex.: documento que estourou o contexto → chunking) e resubmeta só os itens que falharam.
  • Amostra antes do volume: refine o prompt num sample set pequeno (via API síncrona, iterando rápido) ANTES de submeter 10.000 documentos em batch. Um prompt ruim em batch significa milhares de resultados ruins e resubmissões caras — a taxa de acerto de primeira (first-pass success rate) é o que torna o batch realmente mais barato.

2. Review multi-instância e multi-pass (Task Statement 4.6)

Por que self-review é fraco

Pedir ao modelo que gerou o código "agora revise seu próprio código" na mesma sessão rende pouco: o modelo mantém o contexto de raciocínio da geração — as mesmas suposições e decisões que produziram o código continuam presentes, então ele tende a NÃO questionar as próprias escolhas. Nem instruções explícitas de self-review nem extended thinking na mesma sessão resolvem isso, porque o problema não é esforço: é contexto contaminado.

A solução arquitetural: uma instância independente de review — uma segunda chamada ao Claude que recebe APENAS o código gerado (sem o histórico de raciocínio do gerador). Sem o viés de "eu já decidi que isso está certo", a instância fresca pega issues sutis com muito mais consistência.

// GERADOR (instância 1)
const code = await generate({ prompt: taskDescription });

// REVIEWER (instância 2 — sessão limpa, sem o raciocínio do gerador)
const review = await reviewCode({
  prompt: "Review this code for correctness, security and edge cases:\n" + code
  // NÃO inclui: raciocínio do gerador, cadeia de decisões, histórico da geração
});

Multi-pass: attention dilution em reviews grandes

Um PR com 14 arquivos revisado num passe único produz sintomas clássicos: feedback detalhado em alguns arquivos e superficial em outros, bugs óbvios perdidos, e feedback contraditório (o mesmo padrão aprovado num arquivo e reprovado noutro). A causa raiz é attention dilution: com muitos arquivos no contexto, a atenção do modelo se distribui de forma desigual — não é falta de capacidade, é diluição de foco.

A reestruturação correta é multi-pass:

  1. Passes focados por arquivo — um passe por arquivo, analisando issues LOCAIS (lógica, edge cases, segurança daquele arquivo). Profundidade consistente em todos.
  2. Passe de integração cross-file — um passe separado que olha o conjunto focando em data flow entre arquivos: contratos quebrados, tipos que mudaram de um lado e não do outro, chamadas cruzadas. É o que os passes por-arquivo não veem por definição.

Note o que NÃO resolve: context window maior (janela grande não corrige qualidade de atenção), forçar PRs menores (joga o problema no dev em vez de melhorar o sistema), e rodar 3 passes idênticos e exigir consenso (suprime bugs reais detectados de forma intermitente).

Passes por tipo de problema: segurança, lógica de negócio, design de API

Outro sintoma, outra divisão. Mesmo num PR pequeno, um prompt único que pede segurança, lógica de negócio e design de API ao mesmo tempo faz os critérios competirem: os exemplos de um tipo puxam o modelo para aquele tipo, e o recall dos outros cai. Você acrescenta few-shot de injeção de SQL, o reviewer passa a achar mais injeção e começa a perder regra de negócio violada. É o recall trade-off que o objetivo oficial manda evitar.

A estrutura certa são passes especializados por concern, cada um com prompt focado e few-shot próprios: exemplos de vulnerabilidade só no passe de segurança, de regra de negócio violada só no de lógica, de contrato e nomenclatura de endpoint só no de API. Os passes são independentes (rodam em paralelo), e os findings se juntam numa lista só.

As duas divisões se complementam. Por arquivo ataca a diluição por volume (profundidade desigual entre arquivos); por concern ataca a competição entre critérios (um tipo de problema sempre perdido enquanto outro vai bem). Num PR grande dá para combinar as duas, mas o custo multiplica. E o caso oposto: se o recall de um prompt único já atende todos os tipos, separar é custo sem ganho. Regra de bolso: atenção desigual entre arquivos → passes por arquivo + integração; um concern roubando recall de outro → um passe focado por concern, com few-shot próprios.

Verification pass com confidence

Complemento útil: um verification pass em que o modelo revisa os findings e reporta uma confidence self-reportada junto de cada finding. Isso permite calibrated routing: findings de alta confiança vão direto pro dev; os de baixa confiança vão pra fila de triagem humana ou pra um passe adicional. Não trate confidence como verdade — trate como sinal de roteamento.

A palavra que a prova cobra é calibrated. Confiança crua não vale como threshold: antes de rotear, calibre os cortes contra um conjunto rotulado (findings que o time confirmou ou descartou no passado) e só então decida o que vai direto e o que vai pra fila. Repare no contraste com a aula 12 (TS 5.2): lá, confiança autorreportada usada crua como gatilho de escalonamento é distrator; aqui, calibrada com dados rotulados, ela é sinal legítimo de roteamento. E nunca descarte o que ficou abaixo do corte — o que tem score baixo vai pra triagem, não pro lixo.

Regra de bolso: confiança crua não decide nada; calibrada contra dados rotulados, decide para onde cada finding vai.

⚠️ Pegadinha do dia

O distrator mais comum dos dois temas é o "migra tudo / roda tudo de uma vez": migrar TODOS os workflows pra batch por causa dos 50%, ou revisar TODOS os arquivos num passe único com um modelo mais caro. Variações: "polling resolve a latência" (não cria SLA), "context window maior resolve atenção" (janela ≠ qualidade de atenção), "self-review com extended thinking equivale a reviewer independente" (o contexto de raciocínio da geração continua lá). Regra de bolso: batch é decisão de latência, não de custo; review de qualidade é decisão de contexto limpo e foco, não de modelo maior ou mais esforço na mesma sessão.
